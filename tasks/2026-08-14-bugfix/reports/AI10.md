## iOS / PHPicker 事实与 native 实现

Apple API 契约核对后采用以下路径：

- `PHPickerResult` 继续以 `itemProvider` 读取选中项，并保留可选 `assetIdentifier`。
- Live Photo 通过 `NSItemProvider.canLoadObject(ofClass: PHLivePhoto.self)` 识别；仅 richer bridge opt-in 时执行，不对旧 picker 调用产生额外 motion cache。
- `PHAssetResource.assetResources(for: livePhoto)` 获取底层资源：
  - 优先成对使用当前编辑结果 `fullSizePhoto + fullSizePairedVideo`；
  - 若不存在，则成对使用原始 `photo + pairedVideo`；
  - 禁止把 current still 与 original motion 混成伪 pair。
- still 与 motion 使用 `PHAssetResourceManager.writeData` 分别直接写入 DD 自有 `Caches/dd_picker`，不经过 `Data(contentsOf:)`、base64 或 Dart `Uint8List` 承载整段 MOV。
- 普通 photo/video 继续使用现有 `loadFileRepresentation`，并在 callback 生命周期内立即复制到 DD cache。

### Live Photo bridge payload

```text
{
  kind: "livePhoto",
  assetIdentifier?: "...",
  still: {
    path: ".../Caches/dd_picker/...",
    name: "IMG_xxx.HEIC",
    mimeType?: "image/heic",
    size: ...
  },
  motion: {
    path: ".../Caches/dd_picker/...",
    name: "IMG_xxx.MOV",
    mimeType?: "video/quicktime",
    size: ...
  }
}
```

普通 photo/video 仍返回原有 path/name/MIME/size，并附加可选 `kind` / `assetIdentifier`，旧 Dart 解析兼容。

### cache / 大小 / 失败清理

- still、motion 各自继续受既有 `maxBytes` 单文件上限约束。
- 两组件写完后额外检查 `stillSize + motionSize <= maxBytes`，因此 pair 总大小也受同一调用上限约束。
- motion 写入失败：删除已成功的 still。
- 单组件过限/写入失败：删除该组件临时结果。
- pair 总大小超限：删除 still + motion。
- 多选批次中任一项最终失败：删除该批次已经成功写入 DD cache 的结果，避免半批残留。
- Live Photo 可加载但表示/组件不可取得时返回明确 `LIVE_PHOTO_*` 错误，不静默退化成普通 still。

## 服务端媒体授权 / IDOR / 生命周期

新增 migration：

- `000036_live_photo_message_media.up.sql`
- `000036_live_photo_message_media.down.sql`

`message_media.role` 新增 `MOTION`。

发送时：

- still 继续走既有 IMAGE 主媒体授权：`READY + CHAT_IMAGE + sender owns`。
- motion 必须是独立 `READY + CHAT_VIDEO + sender owns + not deleted`。
- 随机引用其他用户 motion media id 返回 `ErrForbidden`，不能拼装跨用户 Live Photo。
- message 写入后 still=`PRIMARY`、motion=`MOTION`。

转发时：

- 只能复用源消息本身已经挂载的 `MOTION`；
- 要求源消息未撤回/未删除、转发者仍是有效成员且没有本地删除该消息；
- 不能在转发请求中替换成别的 motion id。

接收/删除/数据权利：

- Media download 授权本来就按 `message_media` + conversation membership + recall/local-delete 统一判定，因此 `MOTION` 自动进入同一授权边界。
- recall 已删除该消息全部 `message_media`，因此 PRIMARY/MOTION 同时解绑。
- local delete 不物理删共享媒体，但该用户后续无法通过已本地删除消息取得 pair media。
- Saved Messages 旧迁移逻辑按全部 `message_media.role` 复制，因此 `MOTION` 不需要特殊分支。
- Data Rights 删除沿用“仍被共享消息引用的媒体保留并匿名化 owner、私有无引用媒体删除”逻辑；集成测试已增加 Live Photo motion 引用场景。
- down migration 会删除 `MOTION` 关联后恢复旧 role check；这是 rollback 的明确数据降级行为，不能把 down migration 当生产常规回滚策略。
