## 根因结论

### 已确认的代码级故障机制

旧的 `ddFirebaseMessagingBackgroundHandler` 在 killed/background isolate 中复用了完整的 `AppNotificationService.initialize()`。这条完整初始化除了创建 Android channel，还会绑定通知点击回调并读取 `getNotificationAppLaunchDetails()`；其中任一步在后台 isolate 失败，`initialize()` 会把 `_initialized` 保持为 `false`。随后 `showMessage()` 因 `_initialized == false` 直接返回。最外层 background handler 又使用 `catch (_) {}` 全量吞错，因此会形成“FCM 已交给客户端，但本地通知没有显示，而且没有可定位日志”的静默丢通知路径。

这是真实存在的代码缺陷，已修复。

### 同时修正的初始化顺序风险

当前本机解析到 `firebase_messaging 16.5.0`。该版本自带 example 的顺序为：

1. `WidgetsFlutterBinding.ensureInitialized()`；
2. `Firebase.initializeApp(...)`；
3. `FirebaseMessaging.onBackgroundMessage(topLevelHandler)`。

旧 DD 是先注册 background handler，再初始化 Firebase。现已统一通过 `FirebasePushMessagingAdapter.initialize()` 先完成 Firebase 初始化，再注册顶层 handler；background isolate 内同样复用该 Firebase 初始化入口。

此顺序差异是已修正的风险点，但在没有真实设备 FCM 事件证据前，不把它单独宣称为用户现场的唯一根因。

### 尚未最终确认的现场因素

真实设备仍需排除：

- Android 13+ `POST_NOTIFICATIONS` 被拒绝；
- DD 应用级通知被关闭；
- `dd_messages_v2` 通知频道被用户/OEM 关闭；
- OEM 省电/自启动策略；
- 用户实际操作是 Force Stop，而不是普通最近任务划掉；
- 真实设备 endpoint 是否仍为 ACTIVE、Worker 是否成功得到 FCM message name。

因此最终现场根因状态：**代码级 silent-drop 机制已确认并修复；用户设备上的唯一/最终根因尚需真机复测确认。**

## Force Stop 边界

必须区分：

- **前台**：进程活着；
- **后台**：Activity 不可见但进程可能活着；
- **最近任务划掉 / Dart 进程死亡**：不是 Force Stop，FCM high-priority data message 可由 Firebase 官方 service 拉起 background isolate；
- **系统回收进程**：同上，属于本次重点修复状态；
- **设备重启后**：如果包没有处于 stopped 状态，FCM 由 Firebase/Google Play Services 链负责；不同 OEM 的省电/自启动策略仍需实机验证；
- **Force Stop**：Android 将包置为 stopped，直到用户再次明确启动应用前，系统可以阻断 FCM/broadcast。DD 不添加私有保活 service/receiver，也不伪装“可绕过 Force Stop”。

## 真机 ADB 验收步骤（PowerShell，可直接复制）

包名：`org.openimx.client`。以下命令不会打印 FCM token。

### 1. 安装并确认包/进程

```powershell
$pkg = "org.openimx.client"
adb devices
adb install -r .\clients\app\build\app\outputs\flutter-apk\app-debug.apk
adb shell am start -n "$pkg/.MainActivity"
adb shell pm path $pkg
adb shell pidof $pkg
```

登录测试账号，确认 DD 内“通知”页显示：

- `Android 系统通知权限` 为允许；
- `DD 新消息通知频道` 为已开启。

### 2. ADB 检查通知权限与 channel

```powershell
$pkg = "org.openimx.client"
adb shell dumpsys package $pkg | findstr /I "POST_NOTIFICATIONS granted stopped enabled"
adb shell cmd appops get $pkg POST_NOTIFICATION
adb shell dumpsys notification --noredact | findstr /I /C:"$pkg" /C:"dd_messages_v2"
```

如果系统设置里关闭了 DD 应用通知或 `DD 新消息` channel，先恢复后再判断服务端 Push。

### 3. 开启关键日志

```powershell
adb logcat -c
adb logcat | findstr /I /C:"DD Android background push outcome=" /C:"FirebaseMessaging" /C:"FirebaseMessagingService" /C:"Notification"
```

预期 DD 自己的分类只出现类似：

```text
DD Android background push outcome=displayed
DD Android background push outcome=firebaseInitializationFailed
DD Android background push outcome=notificationDisplayFailed
```

不得出现 FCM token 或消息正文。

### 4. 前台对照

保持 DD 前台，从第二账号发消息：

- 只应有一条 DD app-rendered 通知路径；
- 不应出现 FCM 自动渲染的第二条系统通知；
- 检查 sender avatar、DD small icon、点击导航。

### 5. 普通“最近任务划掉”测试

```powershell
$pkg = "org.openimx.client"
adb shell input keyevent KEYCODE_APP_SWITCH
```

在手机最近任务界面**手动把 DD 卡片划掉**。然后检查：

```powershell
adb shell pidof $pkg
adb shell dumpsys package $pkg | findstr /I "stopped"
```

注意：部分 OEM 划掉卡片不会立即杀进程；`pidof` 仍有 PID 不代表失败。确认不是 `stopped=true` 后，从第二账号发送新消息。

验收：

- DD 不需要手动重新打开；
- background handler 可启动；
- logcat 出现 `outcome=displayed`；
- 系统通知显示 sender avatar + DD small icon；
- 点击通知恢复正确 `conversationId`。

### 6. 进程死亡 / 系统回收近似对照

先把 DD 放后台，然后：

```powershell
$pkg = "org.openimx.client"
adb shell am kill $pkg
adb shell pidof $pkg
adb shell dumpsys package $pkg | findstr /I "stopped"
```

`am kill` 与 `am force-stop` 不同；它不应把包置为 Force Stop stopped 状态。此时再从第二账号发消息，预期仍能走 Firebase background isolate 并显示通知。

### 7. Force Stop 控制组

```powershell
$pkg = "org.openimx.client"
adb shell am force-stop $pkg
adb shell pidof $pkg
adb shell dumpsys package $pkg | findstr /I "stopped"
```

此时从第二账号发消息，**不把“不收到通知”判定为 DD bug**。Force Stop 的意义就是验证 Android stopped-package 边界。

### 8. 手动重新打开并验证恢复

```powershell
$pkg = "org.openimx.client"
adb shell am start -n "$pkg/.MainActivity"
adb shell dumpsys package $pkg | findstr /I "stopped"
adb shell pidof $pkg
```

等待 DD 完成 session/Push reconcile 后再次发送测试消息。验收：

- 通知重新可到达；
- endpoint ownership/token refresh 没有因 Force Stop 对照测试损坏；
- 不需要输出或人工抄写真实 FCM token。

### 9. 重启设备测试（可选但建议纳入最终 gate）

```powershell
adb reboot
adb wait-for-device
```

设备启动并解锁后，在**没有执行 Force Stop**的前提下测试 Push。若某 OEM 重启后直到手动启动 DD 才恢复，需要同时记录厂商、Android 版本、后台/自启动/省电策略，不能直接把 OEM 策略误判成 FCM provider 失败。
