## 用户需求

> 全平台应当以备注为唯一显示名，而不是只有详细资料才显示备注。

这里的“唯一显示名”按安全语义解释为：

**当前查看者给某个联系人设置了非空 remark 时，所有面向该查看者的 UI 都优先展示该 remark；没有 remark 才 fallback 对方公开 displayName。**

不是把 remark 变成公共昵称。

## 最重要的隐私约束

`contacts.remark` 是 owner-private：

- Alice 给 Bob 备注“老板”只属于 Alice。
- Carol 看 Bob 时绝不能得到“老板”。
- Bob 自己也不应该因为 Alice 的 remark 而把公共昵称变成“老板”。

因此禁止：

- 把 remark 写回 `users.display_name`。
- 把 viewer 的 remark 永久写进共享 message/group/moment 内容。
- 在不带 principal/viewer 语义的公共缓存里缓存 remark 后发给别人。

## 当前已知缺口

联系人页面部分地方已经：

`remark.isEmpty ? user.displayName : remark`

但 messaging 模型：

`MessagingUserPreview { id, handle, displayName }`

大量直接使用 `users.display_name`。

### 2. 服务端 viewer-relative preview

`COALESCE(NULLIF(contact.remark,''), users.display_name)`

其中 contact join 必须限定：

`contacts.owner_user_id = principal.UserID`

必要时为 API model 增加字段，也可以让现有 `displayName` 在 viewer-relative response 内直接代表 effective display name，但要评估兼容性并加合同测试。

要求：

- direct conversation peer 对当前 viewer 使用 remark。
- lastMessageSender 对当前 viewer 使用 remark（如果是其联系人）。
- group member preview 在“当前 viewer 请求成员列表”时可使用 viewer remark；群内 nickname 与 contact remark 的优先级必须明确并写测试。建议：群专属 nickname 若产品已有语义，先确认需求；不要擅自覆盖管理员设置的群昵称。若需求要求 contact remark 优先，需在 report 写清冲突。
