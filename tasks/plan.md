# 开发实施计划：开源自托管 IM

## 1. 目标

按垂直切片逐步交付一套可自建、多端、邮箱身份的 IM 系统。优先保证账号安全、消息可靠、离线同步和部署可重复，再增加群聊、语音、视频、朋友圈、扫码和端到端加密。

## 2. 开工前假设

以下是假设，不确认就容易中途推翻架构：

1. 首版为单实例自托管，不做跨实例联邦。
2. 用户客户端采用 Flutter；管理后台采用 React + TypeScript。
3. 服务端采用 Go 模块化单体。
4. PostgreSQL 是业务事实数据源，Redis 仅保存可重建状态。
5. 媒体使用 S3 兼容存储，默认 MinIO。
6. 音视频使用自托管 LiveKit 和 TURN。
7. 默认不复制微信品牌资产，只参考用户熟悉的信息架构。
8. MVP 可以先不开放 E2EE，但 1.0 是否必须包含私聊 E2EE 需要负责人确认。
9. 默认部署模式为 Docker Compose。
10. 默认注册策略建议邀请制，部署者可切换公开注册。

## 3. 项目级成功标准

- 全新 Linux 公网服务器可按文档安装。
- 邮箱注册、好友、聊天、媒体、通话、朋友圈和扫码主流程可用。
- 同一消息重试不会重复落库。
- 断线、重启和推送丢失后可增量补齐消息。
- 用户不能越权读取他人会话、媒体或朋友圈。
- 备份可在干净环境恢复。
- Web、Windows、Android、iOS 至少完成受支持版本的构建和核心流程测试。
- 若宣称 E2EE，必须通过官方测试向量、跨平台互操作和独立安全评审。

## 4. 依赖图

```text
产品/架构决策
  ├─ 仓库、CI、代码规范
  ├─ OpenAPI/Event Schema
  ├─ PostgreSQL/Redis/MinIO 基础设施
  │   ├─ Auth/User/Device
  │   │   ├─ Contacts
  │   │   │   └─ Direct Conversation
  │   │   │       ├─ Text Message + Sync
  │   │   │       │   ├─ Media + Voice
  │   │   │       │   ├─ Groups
  │   │   │       │   ├─ Moments
  │   │   │       │   └─ E2EE
  │   │   │       └─ QR Login
  │   │   └─ Push/Notifications
  │   └─ Admin/Moderation/Audit
  └─ LiveKit/TURN
      └─ Calls
```

实现顺序以依赖为准，不按“哪个页面好看”排序。

## 5. 阶段计划

## Phase 0：决策冻结与风险验证

目标：在写业务代码前证明核心技术路线能跑通。

任务：

- 审核 PRD、架构、安全、部署和 ADR。
- 确定正式项目名和许可证。
- 做 Flutter 六端最小构建验证。
- 做 Flutter ↔ Go REST/WSS 最小通信验证。
- 做 Flutter ↔ LiveKit 一对一音视频 PoC。
- 验证目标 VPS 的 UDP/TURN 网络。
- 对 E2EE 候选库做平台、许可证和维护状态评估。
- 决定 iOS 推送模式。

检查点：

- 技术 PoC 通过。
- 高风险依赖没有阻断项。
- 负责人签字确认 ADR。

失败策略：

- Flutter Web 或目标平台插件不可用时，先在 ADR 中改技术路线，禁止带病进入正式开发。

## Phase 1：仓库和工程基础

目标：建立可持续开发的单仓库和质量门。

任务：

- 创建目录结构。
- 初始化 Go、Flutter、React 工程。
- 定义版本、分支、提交和 Release 规则。
- 配置格式化、Lint、单测、构建和依赖扫描。
- 建立 OpenAPI、事件 Schema 和生成代码流程。
- 建立本地 Docker Compose 开发依赖。
- 增加配置加载、日志、requestId、健康检查。

检查点：

- CI 在空业务骨架上全绿。
- 一条示例 API 可被 Flutter 和 Admin 调用。
- 开发环境不需要手工安装 PostgreSQL/Redis/MinIO。

## Phase 2：账号、用户与设备垂直切片

目标：用户能安全注册、登录和管理设备。

顺序：

1. 数据表和迁移。
2. 邮箱验证码。
3. 注册。
4. 登录、Refresh Token 轮换。
5. 用户资料。
6. 设备列表和远程退出。
7. Flutter 注册登录 UI。
8. 管理后台用户只读列表。

检查点：

- 注册到登录端到端通过。
- 重放 Refresh Token 会触发撤销。
- Web Cookie 和原生安全存储策略正确。
- Auth 安全测试通过。

## Phase 3：好友与关系链

目标：用户能安全搜索、申请、接受、删除和拉黑好友。

任务：

- 账号短号精确搜索。
- 好友申请状态机。
- 双向联系人事务。
- 备注和标签。
- 删除、拉黑和权限联动。
- Flutter 联系人和申请 UI。
- 管理后台风控和封禁基础。

检查点：

- 双方并发申请不会产生异常关系。
- 拉黑后消息、朋友圈和通话权限统一受限。
- 搜索和申请限流通过。

## Phase 4：私聊文字消息与可靠同步

目标：交付第一个真正可用的 IM 垂直切片。

任务：

- 私聊会话幂等创建。
- 消息表、会话序号、Outbox。
- 发送消息 API。
- WebSocket 网关。
- 用户级 Sync 游标。
- 历史消息分页。
- 已读序号和未读数。
- 客户端本地 SQLite。
- 离线发送队列、重试和去重。
- 会话列表与聊天页面。

检查点：

- 断网、重连、服务重启不丢消息。
- 同一消息重复提交不重复。
- 双端、多设备顺序可解释。
- 200 在线连接与 100 msg/s 基线压测通过。

这是 MVP 最关键检查点。未通过不得继续堆功能。

## Phase 5：媒体、文件和语音条

目标：安全发送图片、文件和语音消息。

任务：

- 预签名上传。
- 上传确认和对象归属。
- 图片缩略图和 EXIF 清理。
- 文件扫描。
- 配额和临时对象清理。
- Flutter 图片选择、预览、发送。
- 语音录制、波形、取消、播放。
- 桌面拖拽上传。

检查点：

- 未授权用户不能通过对象 URL 下载。
- 恶意类型和超限文件被拒绝。
- 上传失败和断点重试不会产生垃圾消息。

## Phase 6：群聊

目标：在可靠消息底座上增加群聊。

任务：

- 群、成员、角色、邀请和公告。
- 群聊会话与消息。
- 群二维码和审批。
- @成员和已读序号。
- 群管理 UI。
- 群权限和滥用测试。

检查点：

- 被移出成员立即失去新消息和通话权限。
- 大群未读计算不产生每条消息 N 倍写放大。
- 群主转让和解散状态一致。

## Phase 7：一对一语音与视频通话

目标：跨公网、跨运营商稳定通话。

任务：

- 呼叫状态机和数据库。
- LiveKit 房间和短期 Token。
- WebSocket 呼叫信令。
- 多设备来电仲裁。
- Flutter 通话 UI 和平台权限。
- TURN/TLS 和防火墙安装检测。
- 弱网、丢包、UDP 禁止场景测试。

检查点：

- Wi-Fi ↔ 移动网络可通。
- UDP 不可用时 TURN/TCP/TLS 有明确回退。
- 一个设备接听后其他设备停止响铃。
- 不默认录音录像。

## Phase 8：朋友圈

目标：提供好友社交时间线。

任务：

- 帖子、媒体、可见范围。
- Feed 游标分页。
- 点赞、评论和回复。
- 不看谁、不让谁看。
- 举报和管理处置。
- Flutter 发布、列表和详情 UI。

检查点：

- 所有可见范围均有服务端授权测试。
- 直接猜 momentId 无法越权。
- 关系变化和拉黑后可见性符合 PRD。

## Phase 9：二维码与扫码登录

目标：个人码、群码、扫码登录全部使用统一安全模型。

任务：

- QR Payload 版本化。
- 个人名片码。
- 群邀请码。
- 扫码登录状态机。
- 手机确认和设备风险信息。
- Deep Link 路由。

检查点：

- 过期、撤销和重复消费全部失败。
- 二维码不含邮箱、密码、长期 Token 或内部 ID。
- 未经手机确认无法完成登录。

## Phase 10：通知与后台行为

目标：各端在前台和后台获得可解释通知。

任务：

- Web 前台 WSS 和浏览器通知。
- Android FCM 与可选 UnifiedPush。
- iOS APNs 策略实现。
- Windows/macOS/Linux 系统通知。
- 通知隐私预览。
- Push Token 轮换和失效清理。

检查点：

- 通知丢失不影响消息同步。
- 用户关闭预览后不泄露正文。
- Push 供应商失败不阻塞消息落库。

## Phase 11：私聊端到端加密

目标：服务端无法读取私聊消息和附件正文。

前置：候选协议、库和许可证已完成评审。

任务：

- 设备身份密钥。
- 预密钥上传和补充。
- 会话建立和 Double Ratchet。
- 多设备信封。
- 设备验证和安全码。
- 密钥变化提醒。
- 附件客户端加密。
- 本地搜索和密钥备份策略。
- 跨平台测试向量。

检查点：

- 数据库和对象存储抽查无明文。
- Flutter 各端互操作。
- 乱序、重放、新设备、撤销设备场景通过。
- 独立安全评审通过后才能宣传 E2EE。

## Phase 12：管理、风控和合规能力

目标：实例部署者可以安全运营，而不是只能启动容器。

任务：

- RBAC。
- 强制管理员 MFA。
- 用户封禁和会话撤销。
- 举报工单。
- 审计日志。
- 注册策略和风控阈值。
- 容量、健康、错误和队列监控。
- 数据导出与注销。

检查点：

- 普通管理员无法越权成为超级管理员。
- E2EE 正文不能从后台读取。
- 高风险操作均有审计和原因。

## Phase 13：自建部署、升级和灾难恢复

目标：达到“任何人有公网服务器即可搭建”的交付标准。

任务：

- 生产 Dockerfile 和 Compose。
- 安装器。
- 防火墙/UDP/TURN 检查。
- 配置校验。
- 备份和恢复脚本。
- 升级和回滚流程。
- amd64/arm64 镜像。
- 监控和告警模板。
- 完整运维文档。

检查点：

- 干净 Linux 主机安装成功。
- 恢复到另一台干净主机成功。
- 从上一版本升级成功。
- 不依赖作者私有服务。

## Phase 14：稳定性、安全审计与 1.0 发布

目标：从“能运行”提升到“敢公开给别人用”。

任务：

- 全量权限审计。
- 依赖、镜像、Secret、许可证扫描。
- 渗透测试和整改。
- 消息和同步压力测试。
- 弱网和通话测试。
- 数据迁移和恢复演练。
- 无障碍和多端兼容。
- Release 签名、SBOM、Changelog。
- SECURITY、CONTRIBUTING、行为准则。

检查点：

- `docs/06-测试验收与发布标准.md` 全部通过。
- 无未接受的高危漏洞。
- Release Candidate 至少经过一轮真实自建测试。

## 6. 并行开发建议

可并行：

- Flutter Design System 与 Go 基础设施。
- 管理后台与用户客户端。
- 部署脚本与业务功能，只要配置合同先确定。
- LiveKit PoC 与文字消息开发。
- 文档、测试用例和 API 合同。

必须串行或先定合同：

- 数据库迁移。
- Auth → Contacts → Conversations → Messages。
- Message Schema → 客户端本地库 → Sync。
- Device Model → E2EE。
- Call State Machine → 多端 UI。

## 7. 里程碑

### Milestone A：账号可用

注册、登录、资料、设备管理。

### Milestone B：最小 IM

好友、单聊文字、可靠同步、多端基本客户端。

### Milestone C：可日常使用

媒体、语音条、群聊、通知。

### Milestone D：完整微信式核心体验

语音/视频、朋友圈、扫码。

### Milestone E：隐私和自建 1.0

E2EE、安全审计、安装升级备份恢复、完整开源交付。

## 8. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| UI 像素级照抄 | 法务和商店下架 | 原创品牌、Design Token、素材和文案，发布前审查 |
| Flutter 插件跨端不一致 | 某端功能延期 | Phase 0 做真实 PoC，建立平台适配层 |
| iOS 自托管推送 | 后台消息不可靠 | 尽早决定 APNs/中继/自签名模式，并如实文档化 |
| WebRTC 网络复杂 | 通话只在局域网可用 | 强制公网、UDP、TURN、跨运营商测试 |
| E2EE 多设备复杂 | 安全漏洞或消息不可恢复 | 使用成熟协议/库，测试向量和独立审计 |
| 消息重复/丢失 | 核心产品不可用 | 幂等键、序号、Outbox、Sync 游标、故障注入 |
| 公开注册被滥用 | 垃圾账号和骚扰 | 默认邀请制、限流、举报、封禁、新号冷却 |
| 媒体成本失控 | 磁盘和带宽爆炸 | 配额、生命周期、直传、缩略图、容量告警 |
| 微服务过早 | 运维和开发复杂度失控 | 模块化单体，指标证明后再拆 |
| 许可证冲突 | 无法合法发布 | 自动扫描 + 人工审查 + ADR |

## 9. 项目边界

### Always

- 先更新 API/Schema/ADR 再改公共合同。
- 所有外部输入验证。
- 所有资源服务端授权。
- 所有关键写操作幂等或有冲突检测。
- 每个任务包含测试和文档。
- 发布前备份恢复实测。

### Ask First

- 数据库破坏性迁移。
- 新增核心基础设施依赖。
- 修改认证、E2EE、权限和推送模型。
- 改开源许可证。
- 引入跨实例联邦。

### Never

- 提交 Secret。
- 记录消息正文和 Token。
- 自研密码协议或 SFU。
- 用 Redis 作为永久消息事实源。
- 删除失败测试来让 CI 变绿。
- 宣称未经验证的 E2EE 或“一键无脑部署”。

## 10. 估算方式

不在当前企划中承诺固定日期。使用相对复杂度：

- S：单一模块小改动。
- M：一个可测试垂直切片。
- L：跨客户端、服务端和基础设施，需要拆分。
- XL：禁止直接开工，必须继续拆任务。

详细任务见 `tasks/todo.md`。
