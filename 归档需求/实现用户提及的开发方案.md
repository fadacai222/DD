# DD 用户提及（@用户名）开发方案

> 目标：实现类似 Telegram 的 `@username` 用户提及能力。消息中的有效 `@用户名` 以可点击实体展示，点击后打开该用户资料；输入时提供候选补全；服务端负责解析与绑定稳定用户 ID，避免仅靠前端正则造成历史消息失效、伪造或跨端不一致。

---

## 1. 需求目标

### 1.1 用户体验目标

用户在聊天输入框中输入：

```text
你好 @alice
```

发送后：

- `@alice` 以明显的链接/提及样式展示。
- 鼠标悬停时 Windows / Web 显示可点击指针。
- Android / iOS 点击后直接进入该用户资料页。
- 如果对方已是联系人，可在资料页继续发消息、语音或视频通话。
- 如果不是联系人，资料页显示正常的添加联系人能力。
- 如果用户后来修改 DD 号 / handle，旧消息仍然能点击到原用户，不因为旧 `@alice` 文本失效。
- 不存在的 `@xxx` 保持普通文本，不伪造成可点击用户。

### 1.2 输入体验目标

输入 `@` 后进入“提及候选”模式：

```text
@
@a
@ali
```

候选列表：

```text
Alice
@alice

Allen
@allen_01
```

选择候选后自动替换当前触发段：

```text
@ali
```

替换成：

```text
@alice 
```

并将光标放到空格之后继续输入。

### 1.3 本阶段边界

当前项目核心聊天仍以私聊为主，因此本阶段先完整实现：

- 私聊消息中的用户提及实体。
- `@handle` 自动识别。
- 提及候选。
- 点击进入用户资料。
- 编辑、转发、收藏、同步后提及实体不丢失。

群聊上线后直接复用同一套 Message Entity 结构扩展：

- 群内 @成员。
- 被 @ 用户特殊通知。
- 免打扰会话中的“仅提及通知”。
- `@all` / `@所有人`（如果以后产品决定支持）。

不要为当前私聊写一套临时正则方案，之后群聊再推翻重做。

## 2. 当前项目现状分析

已经存在的基础能力：

- 用户拥有全局唯一 `handle_normalized`。
- Handle 规则目前为：

```text
^[a-z][a-z0-9_]{2,31}$
```

- 服务端已有：

```text
GET /api/v1/users/by-handle/{handle}
```

- Flutter 已有：
  - `ContactsApiClient.searchByHandle()`
  - `PeerProfilePage`
  - `MessagingCoordinator`
  - `TextChatPage`
  - `ensureDirectConversation(userId)`

- 消息正文当前存于：

```text
messages.content_json JSONB
```

- `TextContent` 当前已经承载 `text / mediaId / width / height ...` 等字段。

- 文本消息当前直接使用普通 `Text` 渲染。

因此本功能不需要重新设计整个消息系统，只需要在现有 `TextContent` 上增加结构化实体，并补齐用户稳定解析接口及 Flutter 富文本渲染。

## 3. 核心设计原则

### 3.1 不采用“纯前端正则点击”方案

禁止只做：

```text
客户端看到 @alice
→ 正则匹配
→ 点击时再请求 /users/by-handle/alice
```

原因：

1. 用户修改 handle 后旧消息点击失效。
2. 历史消息无法知道当时 `@alice` 指向谁。
3. 前端可以伪造显示和目标用户不一致的提及。
4. Windows / Android / Web / iOS 后续容易出现解析规则不一致。
5. 编辑、转发、收藏、同步都容易丢失语义。

### 3.2 服务端是提及实体的唯一权威

客户端发送的仍然只是文本：

```json
{
  "type": "TEXT",
  "content": {
    "text": "你好 @alice"
  }
}
```

服务端在 `SendMessage` 内：

1. 扫描文本中的 `@handle`。
2. 批量解析这些 handle 对应的真实用户。
3. 生成不可伪造的 `MENTION` Message Entity。
4. 将实体随正文一起写入 `content_json`。

客户端不允许自行指定：

```text
userId
mention target
entity offset
```

即使未来开放第三方客户端，也只能提交文本，由服务端重新生成实体。

### 3.3 使用稳定 userId，不使用 handle 作为跳转主键

`handle` 是用户可修改的人类可读标识。

`userId` 才是稳定身份。

历史消息保存：

```text
显示文本：@alice
绑定目标：userId = UUID
```

即使用户以后改成：

```text
@alice_new
```

旧消息仍然显示原来的：

```text
@alice
```

点击后依然打开同一个人。

## 4. Message Entity 数据结构

### 4.1 服务端结构

在 `server/internal/messaging/models.go` 中增加：

```go
type MessageEntity struct {
    Type   string `json:"type"`
    Offset int    `json:"offset"`
    Length int    `json:"length"`
    UserID string `json:"userId,omitempty"`
    Handle string `json:"handle,omitempty"`
}
```

扩展：

```go
type TextContent struct {
    Text       string          `json:"text,omitempty"`
    Entities   []MessageEntity `json:"entities,omitempty"`
    MediaID    string          `json:"mediaId,omitempty"`
    Width      int             `json:"width,omitempty"`
    Height     int             `json:"height,omitempty"`
    FileName   string          `json:"fileName,omitempty"`
    MIMEType   string          `json:"mimeType,omitempty"`
    SizeBytes  int64           `json:"sizeBytes,omitempty"`
    DurationMS int             `json:"durationMs,omitempty"`
}
```

### 4.2 JSON 示例

消息：

```text
你好 👋 @alice，联系 @bob_01
```

服务端响应示例：

```json
{
  "type": "TEXT",
  "content": {
    "text": "你好 👋 @alice，联系 @bob_01",
    "entities": [
      {
        "type": "MENTION",
        "offset": 6,
        "length": 6,
        "userId": "11111111-1111-1111-1111-111111111111",
        "handle": "alice"
      },
      {
        "type": "MENTION",
        "offset": 16,
        "length": 7,
        "userId": "22222222-2222-2222-2222-222222222222",
        "handle": "bob_01"
      }
    ]
  }
}
```

### 4.3 Offset / Length 标准

这里必须提前固定协议，否则中文、Emoji 会在 Go / Dart / JS 之间错位。

统一规定：

> `offset` 和 `length` 使用 UTF-16 code unit 计数。

理由：

- Dart `String.substring()` 使用 UTF-16 索引。
- JavaScript 字符串也是 UTF-16。
- Flutter / Web 端处理最直接。
- 设计思路与 Telegram MessageEntity 类似。

Go 服务端需要提供专门工具函数，把 UTF-8 字节位置转换为 UTF-16 offset。

严禁混用：

```text
Go rune index
UTF-8 byte index
Dart String index
```

否则文本前面出现 Emoji 时必然错位。

## 5. @Handle 解析规则

### 5.1 当前 Handle 规则复用

直接复用已有：

```go
identity.NormalizeHandle()
```

有效格式：

```text
[a-z][a-z0-9_]{2,31}
```

输入允许用户写大写：

```text
@Alice
```

解析时标准化为：

```text
alice
```

但消息正文不要偷偷修改用户原始输入。

### 5.2 边界判断

应识别：

```text
@alice
你好@alice
(@alice)
@alice，晚上好
@alice/@bob
```

不应错误识别电子邮箱：

```text
hello@example.com
```

不应识别：

```text
@@alice
@a
@alice!!!abc  // 根据 token 边界只识别合法完整段
```

### 5.3 服务端不要依赖 Go regexp lookbehind

Go regexp 基于 RE2，不支持 lookbehind。

推荐写一个小型 ASCII scanner：

1. 遍历文本寻找 `@`。
2. 检查前一个字符是否属于 handle/email 连续字符。
3. 从 `@` 后读取 ASCII：

```text
A-Z a-z 0-9 _
```

4. 最终调用 `NormalizeHandle()`。
5. 记录 UTF-8 byte 起止位置。
6. 转换成 UTF-16 offset / length。

比复杂正则更可控，也更方便写边界测试。

### 5.4 防滥用限制

单条文本已经限制 4000 字符。

进一步限制：

```text
最大 Mention Entity：64
最大不同用户：32
```

超限建议返回明确错误：

```text
TOO_MANY_MENTIONS
```

不要静默丢弃后面的实体，否则用户看到文本却不知道哪些真正生效。

## 6. 服务端用户解析

### 6.1 必须批量查，不允许 N+1

错误做法：

```text
@alice → SELECT
@bob   → SELECT
@carol → SELECT
```

正确做法：

先提取唯一 handles：

```text
alice
bob
carol
```

一次查询：

```sql
SELECT id, handle_normalized
FROM users
WHERE handle_normalized = ANY($1)
  AND status = 'ACTIVE';
```

然后在内存中回填 entities。

### 6.2 不存在用户的处理

例如：

```text
你好 @this_user_does_not_exist
```

服务端：

- 文本正常发送。
- 不生成 entity。
- 客户端显示普通文字。

不要因为一个不存在的用户名导致整条消息发送失败。

### 6.3 拉黑与隐私

提及实体本身只是一个公开身份链接，不应绕过现有权限系统。

点击后资料页仍然必须遵守：

```text
BLOCKED_BY_ME
BLOCKED_BY_PEER
CONTACT
NONE
SELF
```

如果后续产品支持“禁止通过 DD 号被搜索”，提及解析逻辑也必须同步隐私策略。

## 7. 稳定用户资料接口

### 7.1 当前问题

现有：

```text
GET /api/v1/users/by-handle/{handle}
```

只适合当前 handle 查找。

历史 Mention 点击必须通过稳定 userId 打开。

### 7.2 新增接口

建议增加：

```text
GET /api/v1/users/{userId}
```

返回：

```json
{
  "data": {
    "user": {
      "id": "...",
      "handle": "alice_new",
      "displayName": "Alice",
      "bio": "..."
    },
    "relationship": "CONTACT"
  }
}
```

行为与 `SearchByHandle` 返回结构尽量一致。

### 7.3 安全要求

必须：

- 鉴权。
- 只返回公开资料字段。
- 不返回邮箱、设备、IP、登录状态等敏感信息。
- 继续计算关系状态。
- 被删除 / BAN / 非 ACTIVE 用户返回不可用。

## 8. 提及候选接口

### 8.1 API

新增：

```text
GET /api/v1/users/mention-suggestions?q=ali&conversationId=<uuid>&limit=8
```

`conversationId` 当前私聊阶段可选，但保留参数可以为未来群聊做“群成员优先”。

### 8.2 返回

```json
{
  "data": {
    "items": [
      {
        "id": "...",
        "handle": "alice",
        "displayName": "Alice",
        "relationship": "CONTACT"
      }
    ]
  }
}
```

### 8.3 排序优先级

当前私聊阶段：

1. 当前会话对方。
2. 已有联系人。
3. Handle 前缀匹配的其他公开用户。

未来群聊：

1. 群成员。
2. 最近互动成员。
3. 其他可提及成员。
4. 非群成员是否允许展示由产品策略决定。

### 8.4 防止用户枚举

Prefix Search 比现有 exact handle search 更容易被批量枚举。

必须至少做：

- `q` 最少 2~3 个字符。
- `limit <= 8` 或 `<= 10`。
- 鉴权。
- 服务端限流。
- 客户端 200~250ms debounce。
- 客户端取消/忽略过期请求。
- 短期内存缓存相同 query。

不要允许：

```text
q=
limit=10000
```

扫描整个用户库。

## 9. 数据库策略

### 9.1 消息实体不新增独立表

第一阶段不建议创建：

```text
message_mentions
```

原因：

- 当前 `content_json` 已经是 JSONB。
- Mention 是消息正文的一部分。
- 编辑/转发/同步时跟随 Message Content 更自然。
- 当前规模无需单独做 Mention 查询。

因此：

```text
TextContent.entities
```

直接写入 `messages.content_json`。

### 9.2 何时才需要 message_mentions 表

只有未来明确需要：

```text
“查看所有提到我的消息”
“群聊 mentions inbox”
“统计某人被 @ 次数”
```

才增加归一化索引表。

不要现在过度设计。

### 9.3 Handle 前缀索引

当前 `users.handle_normalized` 已 UNIQUE。

在数据量较小时先验证 PostgreSQL EXPLAIN。

如果 Prefix Search 无法稳定走索引，再增加：

```sql
CREATE INDEX users_handle_prefix_idx
ON users (handle_normalized text_pattern_ops)
WHERE status = 'ACTIVE';
```

是否加迁移必须以 EXPLAIN 为准，不要盲加索引。

## 10. SendMessage 改造

发送链路：

```text
Flutter sendText
    ↓
POST /conversations/{id}/messages
    ↓
normalizeSendInput
    ↓
parseMentionTokens(text)
    ↓
resolveMentionUsers(handles)
    ↓
build MessageEntity[]
    ↓
写 content_json
    ↓
outbox / sync
    ↓
其他客户端收到同一份 entities
```

推荐新增内部方法：

```go
func parseMentionTokens(text string) []MentionToken

func (service *Service) resolveMentionEntities(
    ctx context.Context,
    text string,
) ([]MessageEntity, error)
```

不要把 SQL 查询塞进纯解析函数，方便单元测试。

## 11. EditMessage 必须同步重算 Mention

当前已有消息编辑。

用户将：

```text
你好 @alice
```

编辑为：

```text
你好 @bob
```

服务端必须：

- 清除旧 entities。
- 根据新文本重新解析。
- 重新绑定新 userId。
- 与新的 content_json 一起更新。

禁止只更新：

```json
{"text":"..."}
```

而残留旧 Mention Entity。

推荐：

```go
entities, err := service.resolveMentionEntities(ctx, input.Text)
content := TextContent{
    Text: input.Text,
    Entities: entities,
}
```

## 12. Forward / Saved Messages / Sync

### 12.1 转发

当前 `forwardableContent()` 对 TEXT 只复制正文。

必须改为同时复制：

```text
text
entities
```

转发历史消息时应保留原 Mention 绑定。

不要重新按当前 handle 解析，否则用户改名后会把旧内容绑定到错误的人。

### 12.2 收藏

收藏本身保留消息 content_json 时无需额外解析。

但任何“复制成新消息”的路径都必须检查是否保留 entities。

### 12.3 Realtime / Sync

现有同步走完整消息模型。

只要：

```text
Go Message → JSON → Dart ChatMessage
```

都支持 `entities`，无需新增 WebSocket 消息类型。

## 13. Flutter Domain Model

在：

```text
clients/app/lib/features/messaging/domain/messaging_models.dart
```

增加：

```dart
final class MessageEntity {
  const MessageEntity({
    required this.type,
    required this.offset,
    required this.length,
    this.userId,
    this.handle,
  });

  final String type;
  final int offset;
  final int length;
  final String? userId;
  final String? handle;
}
```

`TextMessageContent` 增加：

```dart
final List<MessageEntity> entities;
```

解析时：

- 没有 `entities` 的旧消息必须正常工作。
- 非法 entity 必须忽略，不允许导致整个聊天页崩溃。

兼容策略：

```text
旧消息：entities = []
新消息：entities = [...]
```

无需客户端本地数据迁移。

## 14. Flutter 富文本渲染

### 14.1 替换普通 Text

当前文本消息：

```dart
Text(message.content?.text ?? '')
```

改为独立组件：

```text
MentionRichText
```

建议文件：

```text
clients/app/lib/features/messaging/presentation/widgets/mention_rich_text.dart
```

### 14.2 渲染算法

输入：

```text
text
entities
```

流程：

1. 按 offset 排序。
2. 校验 offset / length。
3. 普通区间生成普通 `TextSpan`。
4. `MENTION` 区间生成可点击 `TextSpan`。
5. 后续普通区间继续生成。

### 14.3 非法实体保护

以下情况直接忽略该 entity：

```text
offset < 0
length <= 0
offset + length > text.length
entities overlap
type == MENTION 但 userId 为空
substring 与 @handle 明显不一致
```

客户端永远不要因为服务器/旧缓存里的坏 entity 导致整个消息列表构建失败。

### 14.4 手势资源释放

如果使用：

```dart
TapGestureRecognizer
```

不要在 `build()` 里无限创建而不 dispose。

`MentionRichText` 建议实现成 StatefulWidget，统一持有并释放 recognizers。

否则长聊天滚动时存在资源泄漏风险。

### 14.5 样式

建议：

收到消息：

```text
蓝色 / DD Link Color
fontWeight: 500
```

自己发送的绿色气泡中：

- 必须保证 WCAG 可读性。
- 不要强行用深蓝导致绿色背景上发黑。
- 可采用较深青色 / link color 的 own-bubble variant。

Windows / Web：

```text
MouseRegion(cursor: SystemMouseCursors.click)
```

Android / iOS：

- 点击态短暂反馈。
- 不弹二次确认。

点击 entity：


```text
MentionRichText.onMentionTap(userId)
```

- 不再强依赖“旧 handle 搜索”才能加载。

加载体验：

- 点击后立即打开资料页骨架。

```text
该用户当前不可用
```

## 16. Flutter 输入框 Mention 触发器

### 16.1 监听方式

在现有：

```text
TextEditingController _composer
```

监听文本与 selection。

只分析当前光标前的局部文本，不要每次整段 4000 字重新做复杂计算。

### 16.2 触发条件

例如：

```text
你好 @ali|
```

`|` 为光标。

向左找到最近一个 `@`，形成：

```text
query = ali
```

如果：

- `@` 已被空格隔断。
- query 含非法 handle 字符。
- 当前正在 IME composing。
- `@` 看起来属于 email。

则关闭候选。

### 16.3 IME 特别处理

现有项目 Android 已经专门处理输入法流畅性。

Mention 功能不能破坏这一点。

当：

```dart
_composer.value.composing.isValid &&
!_composer.value.composing.isCollapsed
```

不要强行替换正文、切 selection 或触发发送。

尤其中文拼音输入阶段避免出现：

- 光标乱跳。
- 键盘收起。
- composing 被清空。
- Android 掉帧。

### 16.4 候选请求

建议：

```text
Debounce: 220ms
```

并使用递增 request token：

```text
request 7 → ali
request 8 → alic
```

即使 7 比 8 晚返回，也必须丢弃 7。

防止候选列表“倒退”。

### 16.5 选择候选

当前：

```text
你好 @ali|
```

选择 Alice 后：

```text
你好 @alice |
```

只替换：

```text
@ali
```

不能粗暴重建整个 TextField value，否则：

- 用户其它文字 selection 丢失。
- IME 状态错乱。
- Undo 行为异常。

## 20. 向后兼容

### 20.1 旧消息

旧 JSON：

```json
{
  "text": "hello @alice"
}
```

客户端正常显示普通文本。

不要客户端自动把所有历史旧 `@alice` 猜成 Mention。

原因：旧消息没有稳定 userId 绑定，自动解析可能把历史用户名绑定到后来注册的新用户。

### 20.2 新消息

新 JSON：

```json
{
  "text": "hello @alice",
  "entities": [...]
}
```

新版客户端富文本展示。

老客户端忽略未知 JSON 字段，仍显示正文。

因此属于兼容式扩展，无需 API v2。

## 21. 安全检查

### 必须保证

- Client 不能伪造 Mention UserID。
- Server 不接受客户端提交 entities 作为事实来源。
- `userId` 点击后仍经过公开资料权限检查。
- Prefix Suggestion 有限流。
- Query 长度有限制。
- Entity 数量有限制。
- 不允许 Entity 越界导致客户端 crash。
- 不把 email / IP / device 等敏感信息放进 Mention API。
- 不允许通过 Mention 绕过 block。

### 重点攻击场景

```text
1. 用户发送 4000 个 @ 触发大量数据库查询
2. 构造 offset 越界让 Flutter substring 崩溃
3. 利用 suggestion 接口枚举全部用户
4. 修改 JSON 让 @alice 点击进入 bob
5. 用户改 handle 后旧消息劫持到后来注册的 alice
6. 转发时重新解析旧 handle 导致绑定变化
```

本方案的“服务端稳定 userId + 批量解析 + entity 校验”就是为了解决这些问题。

## 24. 性能要求

### 客户端

- 输入 `@` 不应造成聊天页明显掉帧。
- 候选网络请求 debounce。
- 候选最多 8~10 条。
- 不因候选显示导致 Android 键盘反复 rebuild。
- 消息富文本不能为每条消息额外发网络请求。
- 只有用户点击 Mention 时才加载资料。

### 服务端

- 单消息 Mention 解析 O(n)。
- 解析数据库查询固定为 1 次批量查询，而不是 N 次。
- 建议候选接口 P95 < 150ms（同区域数据库正常情况下）。
- Prefix Search 是否加索引以 EXPLAIN / 实测为准。

## 29. 最终推荐实现方案

本项目应采用：

```text
文本 + 服务端 Message Entity + 稳定 userId
```

而不是：

```text
前端看到 @xxx 就临时正则成蓝色链接
```

最终链路：

```text
用户输入 @alice
        ↓
服务端解析 alice
        ↓
绑定 alice 当前稳定 UUID
        ↓
消息 JSON 保存 MENTION Entity
        ↓
所有 Flutter 平台统一富文本渲染
        ↓
点击 Entity.userId
        ↓
打开用户当前资料
```

这套实现一次做好后，可以直接成为未来：

```text
私聊 Mention
群聊 @成员
@通知
提到我的消息
Mention 搜索
群聊免打扰例外通知
```

的底层基础，不需要以后推翻重构。
