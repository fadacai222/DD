# P0 E2EE 候选库评估

日期：2026-08-07

## 1. 结论

本轮只做技术选型 Gate，不决定“1.0 必须加密哪些业务”。产品范围仍需要单独冻结。

当前 Go / No-Go：

| 候选 | 结论 | 原因 |
|---|---|---|
| `vodozemac` | **GO：进入跨平台 PoC** | Rust、Apache-2.0、Olm/Double Ratchet + Megolm、官方说明已有 Least Authority 安全审计且无重大问题；Cargo 提供 WASM 随机源特性，适合作为 Native FFI + Web WASM 的统一核心候选 |
| `OpenMLS` | **GO：保留为群聊/多设备 R&D 候选** | RFC 9420 MLS 实现、MIT；CI 构建 Android/iOS/WASM，提供 `js` WASM 特性，但这些目标官方标为 built-not-tested，不能直接当成已验证移动/Web 支持 |
| Signal `libsignal` | **NO-GO：不作为 DD 1.0 直接依赖** | 官方明确“Signal 外部使用不受支持”，桥接/API 可无通知变化；只正式暴露 Java/Swift/TypeScript 包装，Flutter Web 路径不自然；仓库 AGPLv3，会和本项目尚未冻结的许可证形成强耦合 |
| `libsodium` | **NO-GO：不能单独承担消息协议** | ISC、跨平台和 WASM 很好，但它是密码学原语库，不提供设备身份、预密钥、Double Ratchet/MLS、会话恢复、多设备 fan-out 等完整消息协议；可以作为工具库，不能拿来“自己拼一个 Signal” |

因此下一技术动作不是自研密码协议，而是：

```text
Rust crypto_engine 抽象
        ↓
vodozemac PoC
        ↓
Native: Android/iOS/Windows/macOS/Linux FFI
Web: WASM
        ↓
同一组跨平台测试向量
        ↓
再决定是否进入 1.0
```

## 2. 项目约束

DD 的 E2EE 候选至少必须满足：

- Android、iOS、Windows、macOS、Linux、Web 同一协议。
- 多设备账号，不假设“一个用户只有一台手机”。
- 支持离线异步建立会话。
- 前向保密（Forward Secrecy）。
- 会话密钥持续演进，不能长期复用一个静态密钥。
- 服务端只持有密文和必要路由元数据。
- 加密附件使用独立随机媒体密钥，不能直接重复使用消息会话密钥。
- 密钥数据库、备份、设备撤销必须有版本化数据格式。
- Web 端不能为了兼容性退化成另一套弱协议。
- 不自行设计密码学 primitive 或“简化 Double Ratchet”。

## 3. Signal libsignal

官方仓库说明：

- 核心实现为 Rust。
- 对外产品为 Java、Swift、TypeScript 包装。
- 包含 Signal Protocol / Double Ratchet。
- 官方明确写明：**Use outside of Signal is unsupported**。
- JNI、C、Node bridge 以及 API/实现都可能无通知变化。
- 仓库许可证为 GNU AGPL v3。

### 优点

- Signal Protocol 本身是成熟的一对一异步消息协议路线。
- Signal 官方客户端真实生产使用。
- 多设备和预密钥方向与 DD 需求高度接近。

### 阻断风险

1. **官方不承诺第三方稳定性**：升级维护成本不可预测。
2. **Flutter Web**：官方 TypeScript 包装并不等于浏览器 WASM 直接可用于 Flutter Web。
3. **AGPLv3**：DD 的 LICENSE 目前还没冻结，不能先引入一个会强烈影响许可证边界的核心依赖再倒推许可证。
4. **桥接层风险**：如果绕过正式 wrapper 自己接 Rust/C bridge，正好踩进官方声明可随时变化的部分。

### 决策

`NO-GO` 作为 1.0 直接依赖。

可以继续作为协议设计与测试行为参考，但不能因为“Signal 最有名”就把发布路线锁死。

## 4. vodozemac

官方仓库说明：

- Matrix 维护的纯 Rust 实现。
- 实现 Olm（Double Ratchet）和 Megolm。
- 目标是替代旧的 libolm。
- Apache-2.0。
- README 明确记录一次 Least Authority 安全审计，未发现重大问题。
- 当前 Cargo 配置包含 `wasm_js` 特性。

### 优点

- Rust 核心适合统一 Native/WASM。
- 许可证宽松，和 DD 最终选择 MIT / Apache-2.0 / AGPL 等都有较大兼容空间。
- Olm 解决设备对设备 Ratchet；Megolm 提供成熟的群聊发送链思路。
- 已有 Matrix 大规模现实使用背景。
- 有公开安全审计记录。

### 风险

- 这是 Matrix/Olm 体系，不是 Signal 协议。
- DD 仍需要自己定义“设备、公钥、one-time key、fallback key、设备验证、备份”在服务端 API 中如何流转。
- “使用成熟密码协议库”不等于上层 key management 自动安全。
- Flutter Native/WASM bridge 需要我们自己维护稳定边界。

### 决策

`GO` 进入 P0 技术 PoC。

PoC 只验证桥接、测试向量和密钥生命周期，不接入真实聊天 UI，避免未冻结协议就形成历史包袱。

## 5. OpenMLS

官方说明：

- Rust 实现 Messaging Layer Security（RFC 9420）。
- MIT License。
- Linux/Windows/macOS ARM 等目标正式 CI 构建测试。
- Android、iOS、WASM 等目标官方列为 **unsupported, but built on CI**。
- 提供 `js` 特性用于 WASM 编译。

### 优点

- MLS 是标准化群组端到端加密方向。
- 群成员变更和组密钥演进模型比“自己把一对一 Ratchet 拼成群聊”更系统。
- MIT 对开源发布友好。

### 风险

- 当前 DD 最先需要的是稳定的一对一 + 多设备异步消息，直接以 MLS 起步会放大 P0 范围。
- Android/iOS/WASM 尚不能因为“CI 能 build”就宣称可生产使用。
- 仍需要 delivery service、key package、持久化和恢复协议设计。

### 决策

`GO-R&D`：保留为群聊 E2EE 二阶段候选，不作为当前 P0 第一个实现目标。

## 6. libsodium

官方说明：

- ISC License。
- 提供加密、签名、密码哈希等现代 primitive。
- 官方 README 列出 Windows、iOS、Android、JavaScript、WebAssembly 等跨平台能力。

### 优点

- API 稳定、跨平台优秀。
- 许可证简单。
- 可用于特定独立密码学任务。

### 为什么不能直接用它“做 E2EE”

libsodium 不替应用解决：

- 异步预密钥握手。
- Double Ratchet / MLS 会话状态。
- 多设备会话 fan-out。
- 设备撤销。
- session replay / stale key 策略。
- 消息顺序与丢包后的 Ratchet 恢复。

如果拿 primitive 自己设计这些协议，风险远高于收益。

### 决策

`NO-GO` 作为完整消息 E2EE 协议；可以作为其他模块的 primitive 工具候选。

## 7. vodozemac PoC 验收标准

必须全部通过才有资格进入正式 P2/P4 设计：

1. Rust 层同一份核心代码可构建：
   - Windows x64
   - Android arm64
   - iOS arm64
   - macOS arm64/x64
   - Linux x64
   - wasm32
2. Dart Native FFI 与 Flutter Web WASM 输入相同 fixture，输出完全一致。
3. Alice/Bob 离线预密钥建链可成功。
4. 连续 1000 条消息 Ratchet 正常。
5. 消息乱序、重复、丢失后符合协议允许的恢复行为。
6. 旧会话密钥不能解密 Ratchet 后的未来消息。
7. 多设备：Alice-A / Alice-B 与 Bob-A 的 session 独立。
8. 设备撤销后，新的 fan-out 不再包含撤销设备。
9. key material 永不进入普通应用日志、崩溃日志或 HTTP 错误。
10. 加密状态持久化有显式版本号和损坏检测。
11. Web 页面刷新后安全恢复 session，不把长期私钥放进普通 localStorage 明文。
12. 固定跨语言测试向量进入 CI。

## 8. 当前不做的事

- 不自行实现 Double Ratchet。
- 不自行发明新的 AEAD/KDF。
- 不把 E2EE 密钥上传给服务端“方便同步”。
- 不在协议没冻结前把密文格式写死到数据库 migration。
- 不声称“用了成熟库 = 系统已经 E2EE 安全”。

## 9. 对 P1/P2 的接口约束

即便 E2EE 还没正式接入，后面的设备与消息模型必须预留：

- 每台设备独立身份 ID。
- 设备公钥/预密钥 API。
- 密钥版本、算法套件版本。
- 每 recipient device 独立 encrypted envelope。
- 服务端永远不能接受客户端传来的 senderUserId/senderDeviceId 作为权威身份。
- 消息协议必须允许未来在明文 `TEXT` 与 `ENCRYPTED` 间做实例策略迁移。
