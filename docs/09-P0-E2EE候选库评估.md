# 3. 为什么当前不能宣称 E2EE

正式 DD 消息当前仍有：

```text
TEXT content_json
server-side Mention parsing
server-side message search
server-side media authorization
```

服务端可以处理明文内容。

数据库虽然有：

```text
messages.type = ENCRYPTED
media_objects.encryption_mode = E2EE
```

但这些只是协议/schema 预留。

当前没有完整：

- 客户端 identity key lifecycle。
- pre-key upload API。
- multi-device session fanout。
- Flutter Rust FFI/WASM bridge。
- ciphertext envelope v1。
- attachment client encryption。
- key verification UI。
- device trust UI。
- backup/migration。
- cross-platform interoperability suite。
- independent security review。

所以当前状态：

```text
POC AUTO-VERIFIED
PRODUCTION E2EE = PLANNED
```

---

# 4. 核心决策

## 4.1 不自研密码协议

禁止自行设计：

- DH ratchet。
- Double Ratchet。
- identity signature scheme。
- custom crypto primitives。

使用成熟、公开、持续维护的实现。

## 4.2 端侧加解密

最终 E2EE 数据路径：

```text
Flutter plaintext
→ local crypto engine
→ ciphertext envelope
→ DD server stores/routes ciphertext
→ peer device
→ local crypto engine
→ plaintext
```

服务端不得持有会话 private key。

## 4.3 多设备是第一等需求

DD 已经有多设备 session，因此 E2EE 不能只做：

```text
Alice user ↔ Bob user
```

必须设计：

```text
Alice Device A
Alice Device B
Bob Device C
Bob Device D
```

每个目标设备都有独立加密会话/密文信封或等价成熟方案。

---

# 5. 为什么选择 vodozemac 做 PoC

PoC 选择 `vodozemac` 的原因：

- Rust memory safety。
- Matrix 生态实际使用背景。
- 提供 Olm session、account、pickle 等所需基本原语。
- 适合隔离验证异步 pre-key、ratchet、序列化。

但当前 **没有冻结最终生产库**。

正式选型仍需重新检查：

- 2026 年最新维护状态。
- License。
- 安全审计。
- Flutter FFI/WASM 可维护性。
- Android/iOS/Windows/Web 目标支持。
- Protocol interoperability。
- 是否满足当前已存在 P6 群聊的多成员/多设备 E2EE 演进需求。

---

# 6. Web 是最难的目标之一

Flutter Web 无法直接和 Native 一样加载普通 Rust dynamic library。

可能路线：

```text
Rust core
├─ Native: C ABI / flutter_rust_bridge / custom FFI
└─ Web: WASM
```

要求：

- 同一 protocol implementation 尽量复用。
- Native/WASM 输出完全一致的测试向量。
- key serialization 格式版本化。

不能让 Web 单独重写一套 Dart crypto protocol。

# 7. 未来数据模型

## 7.1 Device Identity

现有 `devices` 已预留 identity-key 完整性约束相关字段，但正式 E2EE 前仍需确认最终 schema。

目标数据：

```text
device_id
identity_public_key
signing_public_key
key_version
created_at
revoked_at
```

private key 只在客户端安全存储。

## 7.2 Pre-keys

需要新增独立表/API：

```text
signed_prekeys
one_time_prekeys
```

服务端只存 public material。

## 7.3 Encrypted Message Envelope

目标概念：

```json
{
  "version": 1,
  "algorithm": "...",
  "senderDeviceId": "...",
  "recipients": [
    {
      "deviceId": "...",
      "ciphertext": "..."
    }
  ]
}
```

具体格式必须由选定协议决定，不在本文硬造自定义加密协议。

# 8. 附件 E2EE

未来 IMAGE/FILE/VOICE/VIDEO/STICKER attachment：

```text
random file key
→ local encrypt file
→ upload ciphertext object
→ E2EE message contains encrypted file key/metadata
```

服务端对象存储只看到 ciphertext bytes。

需要处理：

- streaming encrypt/decrypt。
- integrity tag。
- thumbnail/poster 隐私。
- MIME 泄漏。
- file size 泄漏。
- cache encryption at rest。

如果 Poster 仍明文上传，则视频内容仍有隐私泄漏；必须在产品层明确。

# 9. E2EE 与现有功能冲突

## 9.1 服务端搜索

当前 `/api/v1/messages/search` 可以搜索明文 TEXT。

E2EE 开启后：

- 服务器不能全文搜索密文。
- 需要客户端本地索引。
- 多设备搜索依赖每台设备的本地同步。

## 9.2 Mention

当前服务端扫描明文生成 authoritative mention entity。

E2EE 下不能继续让服务端看正文。

未来需要：

- 客户端生成 entity；
- entity 和 message 一起被认证/加密；
- 服务端只允许有限的 notification hint，而不能重新解析正文。

这意味着 **当前 Mention 权威策略只适用于非 E2EE 消息**。

## 9.3 举报

E2EE 下管理员不能“直接打开数据库看举报正文”。

需要：

- 举报者主动提交必要明文/证据。
- 审计举报证据来源。

## 9.4 Notification Preview

Push provider 不应收到完整明文。

客户端解密后决定本地显示。

## 9.5 Web 多端

E2EE key migration/设备验证将显著影响 Web 登录体验。

# 10. Key Storage

## Native

- Windows：需要评估 DPAPI/当前 secure storage plugin 的真实安全边界。
- Android：Android Keystore backed secret。
- iOS：Keychain/Secure Enclave 能力。
- macOS：Keychain。

## Web

浏览器无法提供与硬件安全模块完全等价的保证。

需要明确：

- IndexedDB storage。
- key wrapping。
- session loss/recovery。
- XSS 对 key 的致命威胁。

---

# 11. Device Verification

未来产品：

- 新设备加入提示。
- 设备列表展示 key fingerprint。
- 安全码/二维码验证。
- key change warning。
- revoke device。

多设备 E2EE 没有这个 UX，用户无法发现中间新增的恶意设备。

---

# 12. Key Backup / Migration

必须在上线前做决策：

### 方案 A：无云备份

优点：服务端拿不到恢复 secret。

缺点：设备全丢则历史密钥可能永久丢失。

### 方案 B：用户密码/恢复码加密备份

服务端存 encrypted key backup。

要求：

- recovery secret 客户端持有。
- KDF 足够强。
- 服务端无法离线轻易爆破。

### 方案 C：设备间迁移

旧设备扫描/确认新设备。

最终可以组合 B+C。

---

# 13. 群聊加密

P11 初期建议先解决 **一对一私聊**。

GROUP E2EE 不应直接把所有 pairwise Olm 会话粗暴 N² 发消息作为最终方案。

群聊协议需要另外评估：

- Megolm 类 group ratchet。
- MLS。
- 其它成熟实现。

形成单独 ADR 后再开发。

# 15. 测试要求

必须有固定测试向量：

- first pre-key message。
- bidirectional ratchet。
- out-of-order。
- duplicate ciphertext。
- session restore。
- wrong key restore failure。
- key rotation。
- multi-device。
- revoked device。
- Native ↔ Web WASM。
- Native ↔ Native 不同平台。

Fuzz：

- malformed ciphertext。
- oversized envelope。
- corrupted pickle。
- unknown version。

# 16. 上线阻断条件

以下任何一项未完成都不能显示“E2EE 已保障”：

- [ ] 正式协议和库 ADR Accepted。
- [ ] 所有目标平台加解密互操作。
- [ ] Multi-device。
- [ ] Key verification。
- [ ] Attachment encryption。
- [ ] Restart/persistence。
- [ ] Revoked device 行为。
- [ ] Backup/migration 决策。
- [ ] Fixed test vectors。
- [ ] Independent security review。
- [ ] Threat model 更新。

截至 2026-08-11 当前仍未达到，所以产品必须继续把 Production E2EE 标为 `PLANNED`；P6 Group/P7 Calls/P8 Moments/P9 QR 的实现不改变这一结论。
