# 3. 关系状态

当前公开关系模型主要：

```text
SELF
NONE
PENDING_OUTGOING
PENDING_INCOMING
CONTACT
```

客户端历史代码中可能存在：

```text
BLOCKED_BY_ME
BLOCKED_BY_PEER
```

但当前服务端 `relationshipForUser()` 对任意双方 block 走 `ErrNotFound` 隐私语义，所以 **不能要求公开 profile API 始终告诉调用者谁拉黑了谁**。

产品 UI 需要区分：

- 本人本地已知“我拉黑了谁”（来自 block list）。
- 公开 user lookup 返回不可见。

不能通过多接口拼接破坏隐私边界。

# 4. DDID 搜索

```text
GET /api/v1/users/by-handle/{handle}
```

特点：

- exact handle。
- normalize。
- rate limit。
- 返回公开 user + relationship。
- block 时隐藏存在性。

不做：

- 邮箱公开查人。
- 全库无约束 fuzzy user search。

未来全服务器搜索如果开放，需要独立隐私策略。

# 5. Stable-ID 用户资料

```text
GET /api/v1/users/{userId}
```

这是资料跳转的正式稳定入口。

原因：

- DDID 以后可能允许修改。
- Mention entity 使用 stable userId。
- 历史消息头像/资料跳转不能只靠旧 handle。

服务端：

```text
SELECT ACTIVE user
→ block privacy check
→ expire stale request
→ calculate relationship
```

---

# 6. 当前资料页兼容恢复

历史真人测试发现：多个正常联系人打开后显示“用户不可用”。

客户端当前 `_loadRelationship()` 已增加兼容逻辑：

1. 首选 `GET /users/{stableId}`。
2. 如果 404，可能是旧开发服务端还没有 stable-id route。
3. 仅在能证明同一个用户仍存在时 fallback：
   - exact handle lookup 且 returned userId 相同；或
   - contacts list 中存在相同 userId。
4. 如果仍不能证明，维持 404 不可见。

这套 fallback 的安全目标是：

- 兼容旧服务端。
- 不把 500/网络错误误显示“用户不可用”。
- 不绕过真实 block privacy。

状态：

```text
FIXED-PENDING-RETEST
```

真人复测通过后再升级。

# 7. 好友申请

## 7.1 创建

```text
POST /api/v1/contact-requests
```

输入目标 DDID/handle。

服务端检查：

- target ACTIVE。
- target != self。
- not blocked。
- not already contact。
- rate limit。
- existing pending conflict/idempotency。

## 7.2 同时反向申请

如果 A→B 已 pending，B 又发 B→A：

应收敛为接受关系，而不是永远两条 pending。

服务集成测试覆盖此类竞态。

# 8. 好友申请列表

```text
GET /api/v1/contact-requests?direction=incoming|outgoing&page=...&pageSize=...
```

实际 query 参数以 handler/客户端为准。

- incoming 优先。
- 状态变化后实时刷新。

# 9. 同意好友

```text
POST /api/v1/contact-requests/{id}/accept
```

在一个可靠事务里完成：

```text
lock request
→ verify receiver
→ verify pending/not expired/not blocked
→ create contacts A→B + B→A
→ ensure DIRECT conversation
→ write friend-accepted SYSTEM message
→ update conversation last message
→ wake hidden/archived if needed
→ relationship/message outbox
→ accept request
→ commit
```

这比“先 accept，再客户端自己创建联系人/会话”更可靠。

# 10. 好友通过系统消息

当前服务端在 accept 中插入系统消息：

```text
我刚刚同意了你的好友请求
```

客户端 MainShell 收到该 SYSTEM message 会触发 contacts refresh。

要求：

- 多设备都能通过 Sync 得到。
- 不是仅某个客户端本地 fake bubble。

# 11. 拒绝与取消

```text
POST   /api/v1/contact-requests/{id}/reject
DELETE /api/v1/contact-requests/{id}
```

- reject：receiver。
- cancel：sender。
- 重复动作可返回稳定状态/冲突，不能篡改他人 request。

# 12. Contact 记录

好友关系由两个有方向 contact row 表达：

```text
A owns contact B
B owns contact A
```

每个人自己的 metadata 独立：

- remark。
- starred。
- tags。

A 的备注/标签不能影响 B 的本地联系人视图。


它受服务端关系状态限制，不能被客户端当成“绕过好友申请任意强制成为好友”的普通后门。

# 16. 删除联系人

```text
DELETE /api/v1/contacts/{userId}
```

服务端删除双方 contact pair。

**不删除 DIRECT conversation / messages。**

这样：

- 历史聊天仍可查看。
- 产品可以按策略允许重新发起沟通/好友申请。

删除好友与删除聊天记录是两个独立动作。

# 17. Block

## 17.1 创建

```text
POST /api/v1/blocks
```

服务端：

- 创建 block。
- 删除 contacts pair。
- 取消双方 pending contact requests。
- 写 relationship outbox。

## 17.2 列表

```text
GET /api/v1/blocks
```

用户可明确知道“我拉黑了谁”。

## 17.3 解除

```text
DELETE /api/v1/blocks/{userId}
```

解除后不会自动重新成为好友。

# 18. Block 与 Messaging

Messaging Send 前检查 block state。

期望：

```text
blocked between A/B
→ DIRECT history can remain
→ new write rejected
```

客户端 composer 应锁定并给用户明确关系入口。

# 20. Relationship Outbox

`000012_relationship_outbox` 让 relationship change 进入可靠事件链。

用途：

- 新好友申请。
- 接受/拒绝/取消。
- Block/unblock。
- 联系人变化。

客户端收到 realtime hint 后刷新真实 API/Sync 状态。

# 21. Mention Suggestion 与关系

```text
GET /api/v1/users/mention-suggestions
```

排序优先：

1. 当前 DIRECT peer。
2. Contacts。
3. 其它允许公开匹配用户。

过滤双方 block。

因此 Suggestion 不是“完全开放全站用户枚举”。

# 22. Rate Limit

当前关系模块有 database backed rate event。

至少覆盖：

```text
HANDLE_SEARCH
CONTACT_REQUEST
```

Mention suggestion service 也有 rate limiting。

后续应统一 observability：

- rate limited count。
- abuse source。
- 不记录过多搜索明文。

---

# 23. 并发正确性

必须防：

- A/B 同时申请产生两组 contacts。
- 接受与 block 同时执行。
- 接受与 cancel/reject race。
- 重复 accept 创建重复 DIRECT。

当前 service 使用 transaction/lock/serialization retry 等方式处理。

相关集成测试不能删除。

# 25. 真人测试重点

当前必须重点回归：

1. Windows 打开正常联系人资料。
2. Android 打开正常联系人资料。
3. 联系人打开 3～5 次不随机变“不可用”。
4. 网络断开时显示网络错误/重试，不显示“账号删除”。
5. A 新增 B，B 不重启看到新申请。
6. B 同意，A 不重启看到已成为联系人。
7. 关系通过系统消息出现。
8. Block 后资料隐私与发消息一致。
9. Unblock 不自动恢复好友。
