# P3 好友与关系链

> 状态：核心后端、正式 API、Flutter 管理 UI 和真实 PostgreSQL 并发验证已完成；跨消息/朋友圈/正式通话的拉黑联动要在对应正式模块落地时继续接入。
> 日期：2026-08-08

## 1. 本批目标

P3 的目标不是做一个“联系人页面壳子”，而是先把好友关系本身做成后续消息、朋友圈、通话都能复用的正式授权底座：

```text
精确 Handle 搜索
→ 好友申请
→ 接受 / 拒绝 / 撤销 / 过期
→ 双向好友关系
→ 创建或复用私聊会话
→ 备注 / 标签 / 星标
→ 删除好友
→ 拉黑 / 解除拉黑
```

所有写操作都要求正式 P2 Access Token，不能用 P0 PoC 身份代替。

## 3. 数据模型

Migration：

```text
server/migrations/000004_contacts.up.sql
```

新增表：

```text
contact_requests
contacts
contact_tags
blocks
relationship_rate_events
conversations
conversation_members
```

其中 `conversations` / `conversation_members` 提前放入 P3，是因为“接受好友时必须原子创建或复用私聊会话”属于 P3 Acceptance；正式消息、Outbox、Sync 仍属于 P4。

### 3.1 contact_requests

状态：

```text
PENDING
ACCEPTED
REJECTED
CANCELLED
EXPIRED
```

核心约束：

- 不能给自己发申请。
- `expires_at > created_at`。
- PENDING 时 `resolved_at` 必须为空。
- 已结束状态必须有 `resolved_at`。
- 同一用户对在任一方向最多只有一条 PENDING 申请。

用户对唯一性使用：

```sql
LEAST(sender_user_id, receiver_user_id)
GREATEST(sender_user_id, receiver_user_id)
```

因此 Alice→Bob 和 Bob→Alice 不会同时形成两条长期悬挂申请。

### 3.2 contacts

好友关系使用**双向两行**：

```text
Alice owner -> Bob contact
Bob owner   -> Alice contact
```

备注、标签、星标属于 owner 自己的数据，因此 Alice 给 Bob 的备注不会影响 Bob 看到 Alice 的资料。

### 3.3 blocks

拉黑是单向记录：

```text
owner_user_id
blocked_user_id
```

但好友申请和后续正式业务授权使用“任意方向存在 block 即阻断”的规则。

## 4. 精确 Handle 搜索

接口只支持完整 Handle：

```text
GET /api/v1/users/by-handle/alice_01
```

当前刻意**不做**：

- 全库昵称模糊搜索。
- 邮箱搜索结果泄露。
- 无限制联系人枚举。

返回公开字段只有：

```text
id
handle
displayName
bio
relationship
```

不会返回邮箱。

如果两人任一方向已经存在拉黑，搜索统一返回 `404 NOT_FOUND`，不告诉调用方“你被拉黑了”。即使调用方绕过搜索、直接拿已知 Handle 发送新好友申请，也同样按“目标不可见”返回 404，避免用 409/404 差异枚举 block 状态。

搜索默认限流：

```text
每用户 10 分钟最多 60 次
```

限流事件落 PostgreSQL，而不是只放进单进程内存，因此服务重启不会瞬间清零。

## 5. 好友申请状态机

默认申请有效期：

```text
30 天
```

发送申请默认限流：

```text
每用户 24 小时最多 30 次新申请
```

### 同方向重复提交

Alice 已经有一条 Alice→Bob PENDING 时再次提交：

```text
不新增第二条
返回原 PENDING
```

这样客户端重试不会制造垃圾申请。

### 反方向同时申请

如果 Alice→Bob 已经 PENDING，Bob 此时又申请 Alice：

```text
直接接受已有申请
→ 创建双向 contacts
→ 创建 / 复用 DIRECT conversation
```

真实 PostgreSQL 并发测试中还专门同时启动 Alice→Carol 和 Carol→Alice 两个事务。

最初测试暴露 PostgreSQL `SERIALIZABLE` 的 `SQLSTATE 40001`，已在好友申请和接受事务中加入受控自动重试；修复后真实并发测试通过。

## 6. 接受好友必须原子完成

接受申请在同一 PostgreSQL 事务中完成：

```text
锁定用户对
→ 再检查 block
→ 写 Alice→Bob contact
→ 写 Bob→Alice contact
→ 创建 / 复用 DIRECT conversation
→ 激活双方 conversation_members
→ request = ACCEPTED
```

不会允许出现：

```text
Alice 认为已经是好友
Bob 数据里却没有 Alice
```

也不会为同一用户对重复创建多个逻辑私聊。

私聊唯一键使用排序后的两个 UUID：

```text
smallerUserUUID:largerUserUUID
```

删除好友后历史会话不会被删除；重新加好友时复用原逻辑会话。

## 7. IDOR / 授权边界

当前限制：

- 只有接收方能接受 / 拒绝申请。
- 只有发送方能撤销申请。
- 只能修改自己 owner 视角下的联系人备注 / 标签 / 星标。
- 只能删除自己参与的好友关系。
- 只能解除自己创建的 block。
- 无 Bearer Token 不能访问好友 API。

HTTP 自动测试明确覆盖了：

```text
未登录搜索 → 401
被拉黑搜索 → 404
操作别人的好友申请 → 403
pageSize > 100 → 400
不支持 Method → 405 + 正确 Allow Header
```

## 8. 删除好友语义

删除好友会删除：

```text
Alice→Bob contact
Bob→Alice contact
```

不会删除：

```text
DIRECT conversation
历史消息（P4 后）
```

也就是说“删除好友”和“清空聊天记录”是两个独立动作。

## 9. 拉黑语义

当前 P3 已经立即完成：

```text
创建 block
→ 删除双方好友关系
→ 取消双方尚未处理的好友申请
→ 后续 Handle 搜索不再暴露被拉黑方
→ 直接向已知 Handle 发新申请也伪装为目标不可见
→ 后续好友申请被拒绝
```

并提供：

```go
IsBlockedBetween(ctx, userA, userB)
```

供 P4 消息、P7 正式通话、P8 朋友圈等模块统一做跨模块授权。

### 当前跨模块联动状态

P4 正式消息已经落地拉黑联动，并用真实 PostgreSQL 验证：

```text
拉黑后：禁止发送新的正式文字消息
拉黑前：旧会话 / 旧历史仍允许读取
```

因此“拉黑阻断正式消息”这一项现在有正式实现和自动测试证据。

仍不能声称完成的是：

```text
拉黑已经阻断正式朋友圈（P8 尚未落地）
拉黑已经阻断正式通话（P7 正式模块尚未完成；P0 PoC 不算）
```

P3-007 总验收继续保持未完成，直到 P7 / P8 对应正式模块也完成联动。
