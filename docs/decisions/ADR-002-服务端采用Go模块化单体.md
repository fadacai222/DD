# ADR-002：服务端采用 Go 模块化单体

## 状态

Proposed

## 日期

2026-08-07

## 背景

系统需要长连接、消息同步、媒体控制、朋友圈和管理功能。首版若直接拆微服务，会引入服务发现、分布式事务、消息总线、链路追踪和部署复杂度。

## 决策

核心服务端使用 Go，采用模块化单体：

- 一个 Core API 部署单元。
- 一个 Worker 部署单元。
- 模块拥有清晰接口和数据访问边界。
- PostgreSQL Outbox 处理可靠异步事件。
- 只有在指标证明瓶颈后才拆服务。

## 理由

- Go 适合 WebSocket 和网络服务。
- 容器镜像和单二进制部署简单。
- 模块化单体可使用本地事务保证关键一致性。
- 减少个人和小团队部署负担。

## 备选方案

### Python FastAPI

优点：开发快、生态熟悉。

未采用为核心的原因：大规模长连接和高并发下需要更谨慎的进程模型与资源规划。Python 仍可用于运维脚本、AI/语音转写插件和离线任务。

### Node.js/NestJS

优点：全栈 TypeScript。

未采用原因：可行，但首版希望服务端二进制、并发模型和资源占用更直接。

### 微服务

拒绝原因：当前没有团队规模和流量证据支撑。

## 后果

- 必须通过代码结构和 CI 防止模块互相穿透。
- 单体内部接口仍需契约测试。
- 未来拆分前先记录指标、边界和迁移 ADR。
