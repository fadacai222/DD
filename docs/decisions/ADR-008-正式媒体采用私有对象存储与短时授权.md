# ADR-008：正式媒体采用私有对象存储 + Reservation + 短时授权

## 状态

Accepted

## 日期

2026-08-10（对现有实现补录）

- 当前实现复核：2026-08-11

## 背景

DD 私有媒体包含聊天图片、GIF、文件、语音、视频、Sticker，以及 P8 Moments 图片/视频。直接把大文件经 Go API 全量中转，会增加：

- API 内存/带宽压力。
- 请求超时。
- 横向扩展成本。

如果把 Bucket 公开，又会造成消息附件越权和永久 URL 泄漏。

## 决策

正式媒体采用：

```text
PostgreSQL metadata/authorization
+ private S3-compatible object storage
+ upload reservation
+ presigned direct upload
+ complete verification
+ short-lived authorized download URL
+ client local cache
```

当前开发对象存储使用 MinIO。

## 上传

```text
Client computes metadata/hash
→ POST /api/v1/media/uploads
→ Server creates UPLOADING media + reservation
← uploadId/mediaId/presigned PUT
→ Client PUT directly to object storage
→ POST /uploads/{uploadId}/complete
→ Server validates object
→ READY
→ Business message may reference mediaId
```

## 为什么需要 Reservation

Reservation 固定：

- owner。
- purpose。
- expected size。
- expected sha256。
- expiry。
- target storage key。

这样业务消息不能随意引用一个“不知道是什么”的对象。

## Retry

PUT 失败后：

- 默认重新申请新 reservation。
- 避免新文件 bytes 与旧 expected hash/size 组合。

Complete 可按幂等合同有限重试。

## Cancel

客户端取消必须真正关闭 PUT transport。

服务端未完成 reservation 由 TTL/Worker 清理。

## 下载

```text
Client has mediaId
→ POST /media/{mediaId}/download-url
→ Server verifies current user can read
← short TTL URL
→ Client direct GET object storage
```

Bucket 不 public-read。

## 本地缓存

短期 signed URL 不是长期 cache key。

客户端持久缓存围绕：

```text
stable mediaId
```

Native：

- `.part` download。
- expected-size validation。
- atomic commit。
- LRU/age cleanup。

## 消息媒体

`message_media` 表关联：

```text
PRIMARY
THUMBNAIL
```

VIDEO：

```text
PRIMARY = video object
THUMBNAIL = poster object
```

主视频和 Poster 必须是不同 mediaId。

## Sticker

Sticker 也复用媒体层，但发送权限不能只依赖“对象能下载”。

Custom owner / Telegram subscription 等业务授权由 Sticker domain 判断。

## Orphan Cleanup

Worker 删除 READY object 前必须确认没有所有业务引用，包括：

- message_media。
- custom_stickers。
- telegram_sticker_items。
- 后续新业务引用。

只按 `owner_user_id IS NULL` 删除是错误做法。

## 头像例外

当前 `profile_avatars` 仍是 PostgreSQL bytea 过渡实现。

长期应迁入本模型，但迁移需要兼容现有 profile/avatar URL，不能直接删表。

## E2EE

当前聊天与 Moments 对象内容均未正式 E2EE。

未来 E2EE attachment 仍可复用对象存储，但 bytes 改为客户端 ciphertext，file key 放端到端加密 envelope。

## 备选方案

### 所有 bytes 经过 Go API

拒绝作为默认：高带宽和内存成本，削弱对象存储价值。

### Public Bucket + UUID URL

拒绝：UUID 不是访问控制，URL 泄漏后长期可读。

### 永久 signed URL

拒绝：等价弱化为 public capability，难撤销。

## 后果

正面：

- API 不承担大文件流量。
- 私有媒体授权清晰。
- 可使用云 S3/MinIO。
- 客户端缓存体验好。

成本：

- 需要 reservation/complete 两阶段。
- CORS/对象存储部署更复杂。
- Worker cleanup 必须正确。

## 约束

- 新媒体类型必须声明 purpose/size/MIME/授权。
- 不得直接在 message JSON 中塞任意外部 URL 作为正式私有媒体。
- Presigned URL 不进入长期数据库业务字段。
- Cache 以 stable media identity 为核心。
