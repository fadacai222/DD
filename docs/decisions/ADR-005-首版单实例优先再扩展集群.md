# ADR-005：首版单实例可用优先，再按指标扩展集群

## 状态

Accepted

## 日期

- 提议：2026-08-07
- 确认落地：2026-08-10
- 当前实现复核：2026-08-11

## 背景

DD 的第一目标是让个人、小团队和普通部署者能可靠自托管，而不是从第一天就维护 Kubernetes、多地域、分片数据库和几十个服务。

同时即时通讯又必须为未来多 API 节点留下扩展路径。

## 决策

第一阶段优化顺序：

```text
单实例可部署
→ 单实例可靠
→ 可观测
→ 性能指标
→ 横向扩 API/Worker
→ 必要时拆瓶颈模块
```

当前架构通过以下机制保留水平扩展能力：

- PostgreSQL 作为统一事实库。
- Outbox/Sync 解耦实时通知与数据正确性。
- Redis 作为可选跨节点 realtime hint bus。
- S3/MinIO 独立对象存储。
- LiveKit 独立 RTC 基础设施。
- Worker 可独立扩实例。

## 当前真实形态

开发/最小部署主要可以理解为：

```text
1 × Go API
1 × Go Worker
1 × PostgreSQL
0/1 × Redis
1 × S3/MinIO
1 × LiveKit
1 × SMTP provider
```

生产多节点尚未形成完整部署模板和容量验证。

## 为什么不是“永远单机”

本 ADR 只规定**优先级**，不限制未来集群。

触发扩容的指标包括：

- API CPU/内存长期饱和。
- WebSocket connection 数达到单节点安全容量。
- Outbox backlog P95 持续超目标。
- PostgreSQL 成为瓶颈。
- Media/Push Worker backlog。
- LiveKit RTC capacity。

## 多 API 节点前提

至少：

- Redis/realtime bus 可靠部署。
- API 无关键进程内业务状态。
- Calls 已完成 PostgreSQL 持久化与多设备仲裁；后续多 API 节点需要继续验证锁/恢复/Realtime 行为。
- Session/Rate limit 不依赖单机内存事实。
- P10 Push Job/endpoint 也必须持久化，不能把离线通知状态放 Worker 内存。
- Reverse proxy 支持 WebSocket。
- readiness/metrics 完整。

历史 Calls 曾是明显阻断例；P7 已把 Call state 迁入 PostgreSQL。当前新的横向扩展关注点转为 P10 Push Worker backlog、RTC capacity、Realtime fanout 和数据库热点。

## 备选方案

### 一开始 Kubernetes + 微服务

拒绝：

- 对开源自托管用户过重。
- 开发者精力被基础设施消耗。
- 当前没有流量指标证明需要。

### 单进程内存数据库

拒绝：不能满足可靠消息和重启恢复。

## 后果

正面：

- 自托管门槛低。
- 本地开发简单。
- 容易调试事务与数据一致性。

风险：

- 如果模块偷偷依赖进程内状态，未来扩容困难。
- PostgreSQL schema 耦合需要持续治理。

## 约束

- 新业务状态默认持久化，不把关键事实只放内存。
- Redis 不作为唯一 durability store。
- 拆服务必须有性能/组织证据并新增 ADR。
- 生产模板优先支持一台服务器完整部署，再提供可选外部 Postgres/S3/LiveKit。
