# DD 产品体验与 UI / 功能基线

> 冻结日期：2026-08-08
> 状态：Accepted，后续客户端设计和聊天功能开发必须以本文件为准。

## 1. 一句话定位

DD 的产品方向明确为：

```text
视觉与交互习惯：参考微信
功能丰富度、开放性和限制策略：参考 Telegram
品牌、图标、素材和 Design Token：DD 原创
WhatsApp：不作为 UI / 产品体验参考
```

这不是“把两个 App 拼起来”，而是明确两条不同的参考轴：

- 微信负责解决“用户一上手就知道哪里能点、聊天界面怎么摆、PC 和手机怎么组织信息”。
- Telegram 负责解决“消息类型够不够丰富、操作限制是否过多、跨设备和开放能力是否足够强”。

## 2. 明确禁止的产品漂移

后续实现必须避免继续向 WhatsApp 风格漂移，包括但不限于：

- 不采用 WhatsApp 式绿色大顶栏作为主要视觉识别。
- 不以聊天壁纸作为界面主要视觉元素。
- 不使用过度圆润、胶囊化、卡片化的 Material 风格堆叠聊天界面。
- 不把桌面端做成“手机界面放大版”。
- 不用 WhatsApp 的双勾视觉作为 DD 的默认已读表达。
- 不以“功能少、限制多、移动端优先”作为产品取舍依据。

## 3. 微信参考范围

### 3.1 信息架构

移动端优先保持用户熟悉的四大入口：

```text
消息
联系人
发现
我的
```

桌面 / Web 使用桌面 IM 思路：

```text
左侧窄导航栏
→ 中间会话 / 联系人列表
→ 右侧聊天主区域
→ 必要时展开详情侧栏
```

### 3.2 聊天视觉

聊天页面应接近微信的克制、低干扰风格：

- 浅灰聊天背景。
- 对方消息使用白色或中性浅色气泡。
- 自己消息使用 DD 自有浅绿色体系。
- 气泡圆角适中，不做超大圆角胶囊。
- 头像、气泡、时间、状态信息密度紧凑。
- 顶部只保留联系人名称和少量必要操作，不做巨大 Header。
- 输入区域始终是聊天页最重要的操作区。
- PC/Web 不使用大面积 Material Card 包裹聊天列表和消息流。

### 3.3 交互习惯

- 点击会话进入聊天。
- 长按 / 右键消息打开操作菜单。
- 长按 / 右键会话打开置顶、免打扰、删除等菜单。
- 图片点击进入查看器。
- 语音条直接在气泡内播放。
- 联系人和会话操作位置尽量符合微信用户直觉。

> 仅参考信息架构和交互心智，不复制微信商标、图标、专有字体、插画、提示音、文案和像素级资产。

## 4. Telegram 参考范围

Telegram 是 DD 的“能力上限”和“开放性”参考，不要求一次性照搬全部功能，但默认方向是：

- 尽量减少人为消息操作限制。
- 强多设备同步。
- 丰富消息类型。
- 丰富消息操作。
- 支持 Emoji、贴纸、GIF 和媒体表达。
- 允许大文件、长历史和跨设备继续使用。
- 为机器人、插件、频道、大群、公开用户名等能力预留扩展空间。

长期能力池包括：

```text
Emoji
自定义贴纸包
图片表情
GIF
图片 / 相册
文件
语音条
视频 / 短视频
回复 / 引用
转发
编辑消息
消息反应 Reaction
收藏 / Saved Messages
搜索
会话文件 / 图片 / 链接分类查看
多账号
机器人 API
频道 / 广播
大型群组
公开用户名
定时消息
投票
```

这些属于产品方向，不代表全部进入当前 P4；具体阶段仍由 Todo 分期控制。

## 5. 当前聊天体验必须补齐的能力

### 5.1 已读状态必须显示在对话框内

后端已有 `lastReadSequence` 不能算“已读功能完成”。客户端必须在消息气泡附近给用户看见结果。

私聊中自己的消息至少区分：

```text
发送中
已发送
已送达
已读
发送失败
```

默认视觉建议：

- 使用小号中文状态文字，如“已读”。
- 状态靠近自己最后一条相关消息，不抢正文注意力。
- 不默认复刻 WhatsApp 双勾。
- 用户关闭“已读回执”后，对方不能继续获得精确已读状态。
- **“Widget 还活着”不等于“用户正在读”。** 自动推进已读必须同时满足：聊天页真实可见、应用处于 resumed、当前 route 就是该聊天；`IndexedStack`、后台 Tab、被其他页面覆盖时都不能偷偷 markRead。
- 未真正读到的新消息必须保留会话红点/未读数；移动端需要提供明确的“标为已读”入口。

### 5.2 PC / Web 回车发送

默认键盘规则冻结为：

```text
Enter       = 发送
Shift+Enter = 换行
```

后续可以增加用户设置：

```text
Enter 发送
Ctrl+Enter 发送
```

但无论如何，PC / Web 不允许只能用鼠标点“发送”。

移动端继续使用软键盘发送按钮，不强制套桌面规则。

### 5.3 Emoji

输入框必须提供 Emoji 入口：

- Unicode Emoji 分类。
- 最近使用。
- 搜索。
- 肤色变体在平台支持范围内可选。
- 插入后仍然作为普通文本的一部分发送，不额外制造自定义协议。

### 5.4 图片表情 / Sticker

“图片表情”作为贴纸系统设计，不和普通聊天图片混为一谈：

- 支持 PNG / WebP 等静态贴纸。
- 后续支持动画贴纸格式时必须有资源上限和安全策略。
- 支持收藏单个贴纸。
- 支持自定义贴纸包。
- 服务端必须能自托管贴纸资源，不强依赖第三方平台。

### 5.5 GIF

必须支持 GIF 动图发送和播放：

- 从本地文件发送 GIF。
- 最近使用 GIF。
- 收藏 GIF。
- 可选接入第三方 GIF 搜索 Provider，但必须是插件式、可关闭的能力。
- 自托管实例在完全不接第三方服务时仍必须能发送本地 GIF。

### 5.6 图片消息

图片发送属于核心聊天能力，不再视为“以后有空再补”的装饰功能：

- 文件选择器选择图片。
- 移动端相册选择。
- 剪贴板粘贴图片。
- 桌面端拖拽图片。
- 上传进度。
- 失败重试 / 取消。
- 缩略图。
- 点击大图预览。
- 多图后续支持相册式组合展示。
- EXIF 和超大图片安全处理遵循 P5 媒体管线。

### 5.7 语音条

语音条属于核心聊天能力：

- 移动端支持按住说话。
- 支持上滑取消。
- 支持录制计时。
- 支持权限拒绝后的恢复指引。
- 气泡内直接播放。
- 显示时长、播放进度和已听状态。
- 后续支持倍速和听筒 / 扬声器切换。

PC / Web 也应支持点击录音，不要求完全模拟手机“按住说话”。

## 6. 撤回 / 删除策略

### 6.1 取消 2 分钟硬限制

旧实现中的“2 分钟撤回”不再符合产品需求。

新规则：

```text
用户撤回自己的消息：默认不设时间上限
```

不得在客户端或服务端硬编码 2 分钟。

撤回仍然必须：

- 校验发送者身份。
- 产生可同步事件。
- 所有设备最终一致。
- 不承诺从备份、服务端审计或已被第三方截取的数据中物理消失。

### 6.2 为双方删除

参考 Telegram 的开放性，私聊后续增加独立操作：

```text
仅本地删除
为双方删除
撤回自己的消息
```

具体 UI 文案必须让用户理解三者差异，不能全部叫“删除”。

## 7. 会话置顶 / 免打扰

服务端 API 存在不等于客户端功能完成。

当前 2026-08-08 真人测试已确认：

```text
Web 端置顶：无效
Web 端免打扰：无效
```

因此这两项状态为“已知缺陷”，P4-015 不得标记完成。

修复验收必须覆盖：

- Web 设置后立即更新 UI。
- 刷新 Web 后仍保存。
- Windows / Android 能读到同一服务端会话偏好。
- 另一设备修改后当前端 Sync 后刷新。
- 取消置顶和取消免打扰同样有效。
- 置顶必须真实影响排序，不只是显示一个图标。
- 免打扰必须在通知系统接入后真实影响通知策略，不只是显示一个图标。

## 8. 输入区目标形态

聊天输入区最终建议结构：

```text
[语音] [输入框........................] [Emoji] [+]
```

`+` 展开：

```text
图片
拍摄
文件
GIF
名片
位置（后续）
```

输入框行为：

- 支持多行。
- PC/Web Enter 发送。
- Shift+Enter 换行。
- 支持粘贴文本和图片。
- 支持拖拽文件 / 图片到聊天区。
- 回复消息时输入框上方显示引用条。
- 草稿必须与当前会话绑定。

## 9. 消息操作菜单

基础菜单：

```text
回复
复制
转发
收藏
撤回（仅自己的消息）
仅本地删除
为双方删除（后续）
```

扩展菜单：

```text
编辑（文本消息）
添加 Reaction
保存图片 / 文件
加入表情
举报
```

菜单必须按消息类型和权限动态显示，不能每种消息都显示一模一样的无效操作。

## 10. UI 与丝滑度验收硬规则

后续任何聊天 UI 提交必须同时满足：

- Windows / Web 桌面布局不得像手机页面拉宽。
- Windows 默认窗口固定以 **881×657** 作为基准验收尺寸；桌面主壳目标比例约为 `60px 左导航 + 240～250px 会话/通讯录栏 + 剩余主内容区`。
- Windows 正式客户端不使用系统默认粗重标题栏：采用 DD 自绘窄窗口栏，同时必须保留拖动、边缘缩放、最小化、最大化、关闭和最大化避让任务栏，不能为了“无边框”牺牲 Windows 基础窗口行为。
- Android 360×640 不得 overflow。
- PC/Web Enter 发送必须可用。
- Shift+Enter 换行必须可用。
- 发送状态 / 已读状态在聊天区域可见。
- 回复状态在发送前和发送后都可见。
- 图片、Emoji、贴纸、GIF、语音入口位置统一。
- 会话置顶必须改变排序。
- 免打扰必须保存并跨端同步。
- 浅色 / 深色主题都要可读。
- 不出现 WhatsApp 式视觉漂移。

### 10.1 丝滑度目标

DD 的视觉骨架参考微信，但**手感和响应速度必须对标 Telegram**。不能出现“功能能用，但动画卡、滚动掉帧、点击后等半天才反馈”的情况。

最低体验目标：

- 60Hz 设备上正常滚动、页面切换、会话打开、菜单弹出保持稳定 60fps；高刷新率设备不得人为锁死在低帧率。
- 关键交互点击后 **100ms 内必须有视觉反馈**，网络请求不得阻塞按钮按下态、菜单弹出或页面切换。
- 常规页面转场和轻量动效以 **150～250ms** 为主，避免拖泥带水的长动画。
- 聊天消息发送采用本地乐观更新：点击发送后立即出现消息气泡，网络确认只更新状态，不等待服务端返回后才插入 UI。
- 会话列表、消息列表必须使用增量更新和局部重建，禁止一条消息到来就整页重建。
- 长历史消息必须虚拟化 / 懒构建，不允许一次性构造全部历史。
- 图片缩略图、头像、Sticker/GIF 等媒体不得阻塞主线程；解码、压缩、缓存要有尺寸和并发限制。
- 输入法、滚动、发送、长按菜单、右键菜单、侧栏展开互不抢焦点，不出现明显顿挫或布局跳变。
- Android 键盘升降不得强迫长历史消息列表每帧重新 layout；优先使用不改变主体布局高度的 IME 策略、`viewInsets` 和合成层位移等低成本方案，最终以 Profile 真机帧耗时验证，不以“看起来还行”代替数据。
- 发送消息后输入框必须继续保持输入焦点；PC 连续发送不要求用户重新点击输入框，Android 不得因为发送时切换 TextField enabled 状态而重建 IME connection；点击聊天空白区域应自然收起软键盘。
- 桌面右键消息/会话菜单采用 Telegram 式紧凑浮层心智：图标在左、文字清晰、危险操作红色、按权限动态显示；移动端长按使用紧凑圆角 Action Sheet，危险操作同样必须红色；禁止套用 WhatsApp 式菜单视觉和操作文案。
- 头像必须在主导航、会话列表、聊天气泡、联系人和“我的”统一使用同一账号资源；加载失败时才回退首字母占位，不允许不同页面各维护一份互不一致的头像。
- 弱网时界面仍保持即时响应；网络失败只改变消息状态，不冻结聊天页。
- Windows / Web / Android 都必须做真实滚动与交互性能验收，不能只看静态截图。

建议性能门：

```text
60Hz 参考设备：慢帧比例 < 1%
关键交互视觉反馈：P95 < 100ms
普通页面切换：主观无明显白屏 / 卡顿
连续快速发送 50 条文字：UI 不冻结、不重复、不乱序
500+ 可见历史消息滚动：无持续性掉帧
```

这些指标是体验门槛，不要求为了跑分做复杂架构；优先使用 Flutter 原生高效组件、局部状态更新、缓存和懒加载解决。

## 11. 当前开发优先级调整

在继续做 Emoji、GIF、图片、语音条或朋友圈等扩展功能前，优先顺序正式调整为：

```text
P4 可靠消息核心保持不回归
→ 第一优先：修 Web 置顶 / 免打扰等当前已知 Bug
→ 第二优先：一次性完成 Windows / Web / Android 微信式 UI 主体重构
→ 第三优先：专项做 Telegram 级丝滑度、动画、滚动、输入与页面响应优化
→ 第四优先：补齐聊天基础交互（已读状态、Enter / Shift+Enter、不限时撤回）
→ 第五优先：Emoji / Sticker / GIF
→ 第六优先：P5 图片发送
→ 第七优先：P5 语音条
→ 再继续群聊、朋友圈等大功能
```

UI 阶段不是只“换颜色和圆角”，而是要先把完整壳子做出来：导航、会话列表、聊天主区、联系人、发现、我的、输入区、消息气泡、菜单、弹层、空状态、加载状态、桌面多栏和移动端导航都统一到同一套设计语言。

理由：聊天是 IM 的核心。当前阶段先把产品做得**一眼像微信式 IM、操作顺手、滚动和响应像 Telegram 一样爽**，再往里面继续填功能，后续新增图片、语音、GIF 等能力才能自然落在稳定的 UI 骨架上，而不是边加功能边反复拆界面。

## 12. 参考原则的边界

- “参考微信”不等于复制微信素材。
- “参考 Telegram”不等于每个 Telegram 功能都必须进入 1.0。
- 新能力必须遵守 DD 的安全、权限、审计、自托管和 E2EE 约束。
- 第三方 GIF / Sticker / Bot 服务必须可选，不能成为自托管核心链路的硬依赖。
- 如果视觉设计与功能开放性冲突：优先保留微信式清晰交互，同时提供 Telegram 式能力，不牺牲功能来保持“像微信”。
