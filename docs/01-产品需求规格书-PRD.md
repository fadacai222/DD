# 产品需求规格书（PRD）

## 1. 文档信息

- 项目代号：OpenIMX
- 文档状态：需求草案，待负责人审核
- 目标版本：MVP → Beta → 1.0
- 产品类型：开源、自托管、多端即时通讯系统

## 2. 产品愿景

让个人、团队和社区能够在自己的服务器上搭建一套不依赖手机号、数据归部署者掌控、用户体验接近主流 IM 的通信工具。

产品体验基线固定为：**UI、布局与交互心智参考微信；功能丰富度、开放性和限制策略参考 Telegram；WhatsApp 不作为设计参考。** 品牌、图标、素材和 Design Token 保持 DD 原创。

产品不追求一开始复刻微信全部生态，而是优先把“身份、关系、消息、同步、通话、朋友圈、扫码和部署”做稳定，同时避免聊天核心长期停留在只有纯文字的简化形态。

## 3. 用户角色

### 3.1 普通用户

- 注册、登录和管理个人资料。
- 添加好友、聊天、通话、发布朋友圈。
- 管理隐私、设备和数据。

### 3.2 群主与群管理员

- 管理群资料、成员、邀请、公告和禁言。
- 处理群内举报和成员行为。

### 3.3 实例管理员

- 配置实例、注册策略、邮件、存储和推送。
- 管理用户、封禁、举报、容量和系统健康。
- 执行备份、恢复、迁移和升级。

### 3.4 部署者

- 使用 Docker Compose 安装。
- 配置域名、证书、SMTP、对象存储、推送和音视频端口。
- 查看健康检查、日志、指标和告警。

## 4. 核心用户旅程

### 4.1 注册并开始聊天

1. 用户打开客户端。
2. 输入邮箱并获取验证码。
3. 设置密码、昵称和唯一账号短号。
4. 完成邮箱验证。
5. 搜索好友账号或扫描二维码。
6. 发送好友申请。
7. 对方通过后进入单聊。
8. 双方发送文字、图片和语音消息。

验收标准：

- 未验证邮箱不能完成注册。
- 相同邮箱和相同账号短号不能重复注册。
- 好友关系建立前，默认不能直接发送无限制消息。
- 用户离线后重新登录可补齐消息。

### 4.2 多设备登录

1. 用户在手机登录。
2. 在 PC/Web 打开扫码登录页。
3. 手机扫描二维码。
4. 手机显示设备、浏览器、IP 粗略位置和有效期。
5. 用户确认后 PC/Web 登录。
6. 新设备进入设备列表。

验收标准：

- 二维码 60～120 秒内失效，具体值可配置。
- 二维码只能使用一次。
- 用户未在手机确认前，PC/Web 不能拿到正式会话。
- 设备可被远程退出。

### 4.3 自建部署

1. 部署者准备公网服务器和域名。
2. 执行安装脚本生成 `.env`。
3. 配置 SMTP 和管理员邮箱。
4. 启动 Docker Compose。
5. 完成数据库迁移和初始管理员创建。
6. 访问管理后台完成实例初始化。
7. 客户端输入实例地址并注册。

验收标准：

- 新服务器不需要手工编译源码。
- 安装失败时必须输出明确原因和修复命令。
- 所有容器具备健康检查。
- 升级前自动检查数据库和磁盘空间。

## 5. 功能需求

## 5.1 注册与登录

### FR-AUTH-001 邮箱注册

- 输入邮箱、验证码、密码、昵称、账号短号。
- 验证码有效期、发送频率和尝试次数可配置。
- 密码至少 10 位，支持密码强度校验和泄露密码黑名单。

### FR-AUTH-002 登录

- 邮箱 + 密码。
- 可选 TOTP。
- 可选 Passkey。
- 登录失败返回统一错误，避免枚举邮箱是否存在。

### FR-AUTH-003 会话管理

- Access Token 短时有效。
- Refresh Token 轮换并可撤销。
- Web 优先使用 HttpOnly Secure Cookie；原生客户端使用系统安全存储。
- 支持设备列表、最后活动时间、远程退出。

### FR-AUTH-004 找回密码

- 邮件链接或验证码。
- 重置后撤销旧 Refresh Token。
- 发送异常登录通知。

## 5.2 用户资料与隐私

### FR-USER-001 资料

- 昵称、头像、签名、地区、账号短号。
- 昵称和头像允许修改。
- 账号短号修改频率受限。

### FR-USER-002 隐私设置

- 是否允许通过邮箱搜索。
- 是否允许陌生人发消息。
- 是否展示在线状态和最后上线时间。
- 是否启用已读回执。
- 通知是否显示消息内容。

### FR-USER-003 数据权利

- 导出个人资料、联系人、朋友圈和消息索引。
- 申请注销。
- 注销进入冷静期，完成后执行可审计的数据删除流程。

## 5.3 好友

### FR-CONTACT-001 搜索

- 按账号短号精确搜索。
- 昵称只允许实例内有限模糊搜索，并严格限流。
- 邮箱搜索默认关闭。

### FR-CONTACT-002 好友申请

- 申请理由。
- 接受、拒绝、忽略。
- 双向好友关系建立后创建或复用私聊会话。

### FR-CONTACT-003 关系管理

- 备注、标签、置顶、删除、拉黑。
- 拉黑后双方实时通信立即受限。
- 删除好友是否删除历史消息由用户选择。

## 5.4 会话与消息

### FR-CHAT-001 会话列表

- 会话头像、名称、最后消息、时间、未读数、免打扰、置顶。
- 多端会话排序一致。

### FR-CHAT-002 消息发送

- 客户端生成 `clientMessageId` 作为幂等键。
- 服务端返回正式消息 ID、会话序号和服务端时间。
- 重试不得产生重复消息。

### FR-CHAT-003 消息类型

首版核心：

- 文本。
- Unicode Emoji。
- 图片。
- 文件。
- 语音条。
- GIF。
- 图片表情 / Sticker。
- 系统事件。

后续扩展：

- 视频。
- 位置。
- 联系人名片。
- 富链接卡片。
- 消息 Reaction。
- 投票等 Telegram 式开放消息能力。

### FR-CHAT-004 消息操作

- 回复、引用、转发、撤回、删除本地、为双方删除、复制、收藏。
- **自己的消息默认允许不限时撤回，不得硬编码 2 分钟限制。**
- 后续支持编辑文本消息和 Reaction；具体阶段由 Todo 控制。
- 撤回不等于从备份、对方设备或审计系统中绝对消失，客户端必须准确说明。

### FR-CHAT-005 同步

- 每个会话维护递增序号。
- 客户端保存同步游标。
- 重连后按游标拉取增量事件。
- 服务端不能只依赖 WebSocket 确保可靠送达。

### FR-CHAT-006 已读与送达

- 发送中、已发送、已送达、已读、失败。
- 私聊客户端必须在**聊天消息区域**显示用户可见的发送/已读状态，不能只有后端 `lastReadSequence`。
- 默认使用克制的文字状态（如“已读”），不默认照搬 WhatsApp 双勾视觉。
- 已读回执可由用户关闭。
- 群聊采用每用户最后已读序号，避免为每条消息写入大量记录。

## 5.5 群聊

### FR-GROUP-001 群生命周期

- 创建群、解散群、退出群。
- 群主转让。
- 管理员设置。

### FR-GROUP-002 成员管理

- 邀请、二维码邀请、申请入群、审批、移出、禁言。
- 群人数上限可配置。

### FR-GROUP-003 群功能

- 群公告、群备注、群昵称、@成员、@所有人权限。
- 群二维码可撤销并有有效期。

## 5.6 媒体与文件

### FR-MEDIA-001 上传

- 客户端请求预签名上传地址。
- 上传完成后调用确认接口。
- 服务端校验大小、类型、哈希和归属。
- 未确认的临时对象自动清理。

### FR-MEDIA-002 处理

- 图片生成缩略图并移除不必要 EXIF。
- 视频转码和封面由异步 Worker 处理。
- 文件执行恶意软件扫描。

### FR-MEDIA-003 配额

- 单文件大小、单用户总容量、实例总容量可配置。
- 达到容量阈值时禁止新上传，但不破坏已有消息。

## 5.7 语音消息

### FR-VOICE-001 录制

- 权限申请、按住录制、取消、超时结束。
- 默认最大 60 秒，可配置。

### FR-VOICE-002 播放

- 波形、进度、已听状态、倍速。
- 移动端支持听筒模式。

## 5.8 音视频通话

### FR-CALL-001 呼叫状态机

状态：

- `INVITING`
- `RINGING`
- `ACCEPTED`
- `REJECTED`
- `BUSY`
- `TIMEOUT`
- `CONNECTED`
- `ENDED`
- `FAILED`

所有终端必须遵守同一状态机，避免多设备同时接听导致状态错乱。

### FR-CALL-002 媒体能力

- 音频通话。
- 视频通话。
- 静音、摄像头开关、前后摄像头切换。
- 网络质量提示。
- 断线重连。

### FR-CALL-003 隐私

- 不默认录制。
- 通话记录只保存参与者、时间、状态和时长。
- 若未来提供录制，必须显式提示所有参与者。

## 5.9 朋友圈

### FR-MOMENT-001 发布

- 文本、图片、短视频。
- 可见范围和位置标签为可选。

### FR-MOMENT-002 互动

- 点赞、评论、回复、删除自己的互动。
- 评论可见性遵循朋友圈可见范围。

### FR-MOMENT-003 屏蔽

- 不看对方。
- 不让对方看我。
- 黑名单自动作用于朋友圈。

### FR-MOMENT-004 管理

- 举报、隐藏、删除、封禁。
- 操作写入审计日志。

## 5.10 二维码

### FR-QR-001 个人码

- 包含短期或可撤销的公开标识，不直接嵌入邮箱或内部数据库 ID。

### FR-QR-002 群邀请

- 可设有效期、使用次数和审批要求。

### FR-QR-003 扫码登录

- 临时会话、一次性、手机确认、风险信息展示。

## 5.11 管理后台

### FR-ADMIN-001 系统配置

- 域名、实例名、Logo、SMTP、对象存储、推送、LiveKit、TURN。

### FR-ADMIN-002 用户管理

- 搜索、封禁、解封、注销、角色、设备撤销。

### FR-ADMIN-003 风控

- 注册频率、验证码频率、登录失败、搜索、好友申请、发送、上传限流。

### FR-ADMIN-004 可观测性

- 服务健康、在线连接、消息吞吐、错误率、任务队列、数据库连接、存储容量。

## 6. UI/UX 需求

### 6.1 设计原则

- 采用“消息、联系人、发现、我的”式信息架构。
- **布局、信息密度、操作位置和用户心智参考微信。**
- **功能能力、消息类型、跨设备体验和限制策略参考 Telegram。**
- **WhatsApp 不作为 UI 或产品体验参考**：避免绿色大顶栏、壁纸中心化、过度胶囊化气泡和“手机界面直接放大到桌面”的设计。
- 不复制微信或 Telegram 的品牌、图标、字体、插画、提示音和像素级布局。
- 建立原创 DD Design Token、组件库和主题系统。
- 支持浅色、深色和跟随系统。
- 桌面/Web 使用左侧导航 + 中间列表 + 右侧聊天的桌面 IM 多栏结构；移动端使用底部导航。
- PC/Web 输入框默认 `Enter=发送`、`Shift+Enter=换行`，并预留可配置发送快捷键。
- 聊天输入区必须预留语音、Emoji、图片/文件/GIF 等入口，不允许长期只保留文本框 + 发送按钮。
- 当前开发顺序固定为：**先修已知 Bug → 先完成完整微信式 UI 主体 → 再做 Telegram 级丝滑度专项优化 → 再继续媒体与高级消息能力。** UI 与手感稳定前，不继续无节制堆新功能。

### 6.2 丝滑度与响应性能

- 视觉与交互骨架参考微信，但滚动、点击、菜单、输入和页面切换的即时感对标 Telegram。
- 60Hz 参考设备上核心页面滚动与转场应稳定接近 60fps；高刷新率设备不得人为锁死在低刷新率。
- 用户点击关键操作后 P95 100ms 内必须出现视觉反馈，网络请求不得阻塞按下态、菜单弹出或页面跳转。
- 聊天发送采用乐观 UI：消息气泡先进入本地列表，再异步更新“已发送 / 已送达 / 已读 / 失败”。
- 会话列表和消息列表使用局部刷新、懒构建和缓存，禁止一条消息到来导致整页重建。
- 长历史消息、图片缩略图、Sticker/GIF 解码不能持续阻塞 UI 主线程。
- 弱网、重连、上传和发送失败只能影响消息状态，不得冻结输入框或聊天滚动。
- Windows / Web / Android 均需使用 Profile/真实设备做滚动、快速发送和长列表性能验收，不能仅凭 Debug 模式主观判断。

### 6.3 无障碍

- 文本缩放。
- 键盘导航。
- 屏幕阅读器标签。
- 色彩对比度满足 WCAG 2.2 AA。
- 不仅使用颜色表达消息状态。

## 7. 业务规则

- 账号短号全实例唯一，大小写归一化。
- 用户删除不自动删除对方设备上已有消息。
- 好友删除和拉黑是不同动作。
- 消息撤回必须产生可同步的系统事件；自己的消息默认不限时撤回。
- 所有写操作支持幂等或冲突检测。
- 服务端时间作为排序依据，客户端时间仅作展示参考。
- 二维码内容不得直接触发高权限操作。
- 任何插件都不得绕过权限、审计和限流。

## 8. 成功指标

### 产品可用性

- 新用户在 3 分钟内完成注册并发送第一条消息。
- 断网恢复后消息不重复、不丢失、顺序可解释。
- 多设备未读数最终一致。

### 部署可用性

- 使用受支持 Linux 系统和 Docker 的新服务器可按文档完成安装。
- 默认安装完成后能通过健康检查。
- 升级失败可回滚应用版本，并对数据库迁移给出明确处置。

### 安全基线

- 无明文密码、验证码和 Refresh Token 存储。
- 无未授权读取他人会话、文件或朋友圈的路径。
- 公开发布前完成第三方安全审计或至少独立代码审计。

## 9. 开放问题

- 正式开源许可证采用 AGPL-3.0 还是 Apache-2.0。
- 1.0 是否强制包含群聊端到端加密。
- 默认注册策略是邀请制还是公开注册。
- 朋友圈短视频最大时长和大小。
- 首版群人数上限。
- 是否提供官方公共实例；默认不建议在项目早期提供。
