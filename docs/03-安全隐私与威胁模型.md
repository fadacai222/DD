# DD 安全、隐私与威胁模型

> 更新时间：2026-08-12 04:40（Groups/Calls/Moments/QR/Push 当前边界复核）
>
> 目标：明确 **当前已经存在的安全边界**、**未来 E2EE 边界**、以及新增媒体/Sticker/Mention 功能带来的攻击面。

---

# 1. 安全目标

DD 当前安全目标：

1. 未授权用户不能读取或修改其他用户的私有数据。
2. 客户端提交的 userId、conversationId、messageId、mediaId 均视为不可信。
3. 密码、验证码、Token、第三方 provider secret 不进入日志。
4. 媒体 Bucket 不公开。
5. Block 不形成易枚举的隐私侧信道。
6. Realtime 丢失不导致业务数据丢失。
7. 第三方 Sticker Relay 不能变成 SSRF / 任意代理。
8. 未实现 E2EE 前，不以任何方式宣称服务端无法看到消息内容。

---

# 2. 当前信任边界

```text
[Untrusted Client]
      │ HTTPS / WSS
      ▼
[Go API Authorization Boundary]
      │
      ├── PostgreSQL            trusted application datastore
      ├── Redis                 untrusted-for-durability hint bus
      ├── S3/MinIO              private object store
      ├── SMTP                  external provider
      ├── Telegram Bot API      external provider
      └── LiveKit/TURN          RTC media infrastructure
```

关键原则：

- 客户端 UI 状态不是权限边界。
- Redis 不是消息事实源。
- S3 presigned URL 只是临时能力，不应成为长期公开 URL。
- Telegram/LiveKit 返回内容属于外部输入，必须校验和限额。

# 3. 关键资产

最高敏感：

- 明文密码（只应瞬时存在于请求处理内）。
- Password hash。
- Access Token。
- Refresh Token。
- `AUTH_TOKEN_SECRET`。
- `EMAIL_CODE_PEPPER`。
- SMTP password。
- S3 access/secret key。
- LiveKit API secret。
- Telegram Bot Token。
- 未来 E2EE private keys。

用户私有数据：

- 邮箱。
- 联系关系。
- 私聊消息。
- 媒体文件。
- 语音/视频内容。
- 设备列表。
- 搜索历史/本地缓存（客户端侧）。

# 4. STRIDE 摘要

| 类别 | 主要风险 | 当前缓解 |
|---|---|---|
| Spoofing | Token 伪造、设备伪装 | 签名 Access Token、Refresh hash、device binding |
| Tampering | 伪造 userId/mediaId/entity | 服务端重新授权、Mention authoritative parse、media purpose/owner 校验 |
| Repudiation | 高风险操作无法追踪 | Auth audit；未来 Admin 审计仍需补齐 |
| Information Disclosure | IDOR、Block 泄露、公开 Bucket | owner/member auth、404 隐私语义、私有 S3 |
| Denial of Service | 大文件、搜索枚举、验证码、Sticker relay | size/limit/rate limit、bounded query |
| Elevation of Privilege | 客户端伪造管理员/群权限 | Group Owner/Admin/Member 已由服务端判定；Admin RBAC 仍未实现 |

# 5. 认证安全

## 5.1 密码

- 使用 Argon2id。
- 不可逆哈希。
- 日志禁止记录明文密码。
- 登录错误尽量避免区分“邮箱不存在”和“密码错误”。

## 5.2 邮箱验证码

当前验证码用途：

```text
REGISTER
PASSWORD_RESET
CHANGE_EMAIL
```

要求：

- 短 TTL。
- 最大尝试次数。
- 单次消费。
- 发送限流。
- 数据库只保存经 pepper 处理后的值。

## 5.3 Access Token

- 短期。
- 服务端验证签名、时效与 Principal。
- 所有业务 API 重新做对象授权。

## 5.4 Refresh Token

- 数据库存 hash，不存明文。
- Rotation。
- family 关系。
- replay 检测后撤销相关 family。
- 远程退出/密码重置应使相关 refresh 无效。

## 5.5 Native secret

Native 客户端使用 `flutter_secure_storage` 封装安全存储。

登录历史只保存可公开/低敏感展示数据，不应保存密码或 Refresh 明文副本。

# 6. 授权模型

## 6.1 用户资料

- `/me` 只操作本人。
- Stable user profile 只返回公开字段。
- 邮箱只在本人 account API 中处理。

## 6.2 联系人

所有请求都以 authenticated `principal.UserID` 为 owner。

客户端提交 `ownerUserId` 不应改变授权主体。

## 6.3 DIRECT 会话

读写前必须验证：

- Principal 是 active member。
- Block 状态不禁止写入。
- message/media/reply 均属于合法上下文。

删除联系人后会话仍可存在，所以“是不是 contact”与“是不是 conversation member”不能混为一个判断。

## 6.4 SELF 会话

只允许本人访问。

如果未来出现 SELF 会话被第二个成员加入，属于严重权限漏洞。

## 6.5 GROUP

P6 已正式实现。Owner/Admin/Member、成员身份、群状态和 join request 均以服务端 PostgreSQL 为事实，不接受客户端 role 字段作为授权依据。

必须持续保证：

- 非成员不能读取/发送 Group 消息；
- 被踢/退出后立即失去 Group 读写权；
- `@all` 只允许服务端确认的 OWNER/ADMIN；
- 管理员不能越过 Owner 专属操作；
- Group QR redeem 必须重新验证群状态、Block、容量、invite 状态；
- 已经同群后双方后来 Block 不应静默篡改历史成员关系，但 Block 不能被用来重新邀请骚扰。

---

# 7. Block 隐私模型

当前 Stable user 查询在检测到双方 block 后返回 NotFound 语义。

目的：

> 让“账号不存在/不可见”与“被关系隐私策略隐藏”对调用者尽量不可区分。

注意：

- 客户端不能通过第二个 API 轻易推断 `BLOCKED_BY_PEER`。
- Mention suggestion 必须过滤双方 block。
- 搜索、资料、消息、群聊、朋友圈、通话和二维码邀请必须一致联动。
- 当前客户端兼容旧服务端的 profile fallback 只能在其它 authenticated relationship endpoint 明确证明同一 stable user 仍存在时恢复；不能破坏 block 隐私。

# 8. 消息安全

## 8.1 Idempotency

`clientMessageId` 与 device 绑定，用于避免重复发送。

不能允许攻击者拿别人的 client ID 覆盖别人的消息。

## 8.2 Reply

服务端验证 reply target：

- 存在。
- 未删除。
- 属于同一会话。

## 8.3 Edit

- 仅发送者。
- 当前只支持 TEXT。
- `expectedEditVersion` 防止并发覆盖。
- 修改正文后 Mention entities 必须由服务端重建。

## 8.4 Recall

- 仅允许拥有撤回权限的发送者/未来群管理员策略。
- 媒体引用需要按产品语义解绑，但不能错误删除仍被其它业务引用的 object。

## 8.5 Local Delete

服务端只写当前 user 的 local deletion，不改变其他成员可见性。

# 9. Mention 安全

## 9.1 威胁

恶意客户端可能提交：

- 假 userId。
- 越界 offset。
- overlap entities。
- `@alice` 文本却绑定 Bob。
- 大量 Mention 造成 CPU/DB 放大。

## 9.2 当前防护

- 普通 Send/Edit 不信任客户端 entity。
- 服务端扫描正文。
- 限制 entity 数量和 unique user 数量。
- 一次批量 SQL 解析。
- offset 使用固定 UTF-16 code unit 语义。
- 客户端渲染时再次忽略越界/overlap/mismatch entity。
- Suggestion query 限长度、limit、字符集并做 rate limit。
- block 过滤。

## 9.3 `@all`

P6 已正式支持 GROUP Mention 规则：

- 只在 GROUP 解析为群体 Mention；
- 只允许服务端确认的 OWNER/ADMIN；
- 普通成员输入 `@all` 不获得群体 Mention 权限；
- DIRECT 中永远只是普通文本；
- 普通 `@成员` 只能绑定当前 active group member。

# 10. 媒体上传安全

## 10.1 不信任的字段

- 文件名。
- MIME。
- size。
- sha256。
- purpose。
- mediaId。

服务端必须用 reservation + complete 合同校验。

## 10.2 Purpose

当前至少：

```text
CHAT_IMAGE
CHAT_FILE
CHAT_VOICE
CHAT_VIDEO
STICKER
GIF
MOMENT_IMAGE
MOMENT_VIDEO
```

消息类型必须匹配媒体 purpose。

例如：

- VIDEO 主对象必须是 CHAT_VIDEO。
- VIDEO poster 使用允许的图像 purpose/role 合同。
- STICKER 消息不能随意引用他人不可发送的媒体。

## 10.3 上传资源限制

必须限制：

- 单文件大小。
- 用户并发 reservation。
- 上传 TTL。
- Sticker 像素尺寸。
- 解码后像素总量，防 zip/image bomb。

## 10.4 对象名

对象 storage key 由服务端生成，不允许把客户端原始路径直接拼接进 Bucket key。

---

# 11. 媒体下载安全

Bucket 必须私有。

下载流程：

```text
mediaId
→ authenticated authorization
→ short-lived presigned URL
```

授权至少考虑：

- media owner；
- message membership；
- custom sticker owner；
- subscribed Telegram pack；
- 当前可见 Moment 的 `moment_media`；
- 当前业务引用。

短期 URL 泄漏风险：

- TTL 尽量短。
- 日志不要记录完整 presigned query。
- 客户端缓存长期保存本地 bytes，而不是长期保存 presigned URL。

# 12. Sticker 安全

## 12.1 Custom Sticker

用户 A 上传的自定义 Sticker 默认不等于用户 B 可再次发送。

授权规则必须明确检查 owner/library。

## 12.2 Telegram Relay SSRF

这是新增高风险点。

**禁止接口接收任意 URL 让服务端抓取。**

正确模型：

```text
client verifies Telegram link
→ extracts setName
→ server only accepts setName
→ server constructs provider API calls itself
```

setName 允许字符集和长度必须受限。

## 12.3 Telegram Bot Token

- 仅环境变量或 `_FILE` secret。
- 不写 Flutter。
- 不写 Git。
- 不写响应。
- Provider 原始错误中如可能包含 token，不原样返回用户。

## 12.4 Provider 内容

- 限 pack item 数。
- 按 Telegram 格式分别限单 item size：静态、TGS、WebM 使用独立上限，外层下载仍有总上限。
- 不只信响应头：静态检查 WebP/PNG 文件签名，TGS 检查 gzip + Lottie JSON 基本结构，WebM 检查 EBML/WebM 容器标识。
- 合法 TGS/WebM 进入 DD 私有对象存储；只有格式损坏、类型标志冲突或超限项目才计入导入失败。
- TGS 解压必须有限制，防止 gzip bomb 造成内存放大。
- provider 返回 file path 不允许绕过预期域/协议边界。

## 12.5 Pack 缓存

同一个 Telegram Pack 可在服务端全局缓存，但用户订阅是独立关系。

用户 A unsubscribe 不得删除仍由 B 使用的 pack/media。

---

# 13. Media Orphan 清理安全

自动清理不能只看 `owner_user_id IS NULL` 或时间。

删除 READY 对象前必须确认没有：

- `message_media` 引用。
- custom sticker 引用。
- telegram sticker item 引用。
- `moment_media` 引用。
- 其它当前/未来业务引用。

否则会造成静默数据丢失。

---

# 14. Realtime 安全

WebSocket：

- 必须鉴权。
- Origin 在生产环境限制。
- 心跳/空闲超时。
- 单连接/单用户资源需要上限。
- 不依赖客户端 event payload 直接修改数据库。

Redis bus：

- 只传播 hint。
- 业务最终状态通过 PostgreSQL/Sync 获取。

# 15. Call / LiveKit 安全

P7 已从 POC 晋升正式服务端状态机：

- LiveKit Token 由服务端签发，客户端不持有 LiveKit API Secret；
- caller/callee 身份来自 Bearer Principal，而不是客户端上传的 identity；
- 只允许当前联系人发起，双方任一 Block 均拒绝；
- Call 状态持久化 PostgreSQL，并通过事务/锁处理并发；
- caller Call 绑定发起设备；callee ringing 可在多设备出现，但第一台 accept 后只有胜出设备有媒体控制权；
- 非胜出设备不能获取 LiveKit token、挂断或修改终态；
- room、participant identity/name 由服务端生成；
- Call 绑定 DIRECT conversation，终态 SYSTEM message 与 Outbox 由服务端事务写入。

仍需生产安全验收：TURN/TLS 公网、token scope/TTL、30 分钟与弱网、服务重启/多节点、审计与滥用限流。

默认不录音录像。

# 16. 通知 / Push 隐私

通知内容属于敏感旁路。

P10 数据模型已经开始定义 `user_notification_preferences`，预览策略当前草案为：

- `FULL`：允许显示正文预览；
- `SENDER_ONLY`：只显示发送者/事件来源，不复制完整消息正文；
- `HIDDEN`：只显示泛化新消息提示。

`device_push_endpoints` 只保存当前设备 provider endpoint 及 hash/状态，`push_jobs` 只保存最小资源引用、actor、dedupe/retry 信息，**不得把 Push 队列变成第二套消息数据库**。

Mention 通知不能绕过 mute。Push 到达后客户端仍应通过 Sync 获取业务真相。

P10 当前 Provider/API/Worker/Flutter 注册链已经实现。2026-08-12 为修复 Android 后台通知 sender avatar，新增短期头像 capability：Worker 使用 `AUTH_TOKEN_SECRET` 对 `userId + expires` 做 HMAC，FCM 只携带 capability URL，不携带 Access/Refresh Token；`HIDDEN` 预览不下发该 URL；HTTP capability 默认 24h、验证端拒绝过期/篡改/超长有效期，生产 origin 必须 HTTPS，开发仅允许 localhost/RFC1918 私网 HTTP。该 URL 只授予对应用户头像读取能力，不授予资料、消息或其它 API 权限；日志仍不得记录完整 capability query。

# 17. QR / 扫码登录安全

P9 服务端已经实现以下安全模型：

### 个人码

- payload 绑定 DD scheme/version 与目标实例；
- userId 只是定位 stable user，最终资料/关系权限仍由 authenticated API 决定；
- 外部实例 payload 不能静默当成本实例用户。

### 群二维码

- 服务端生成随机 invite nonce；
- 只有 OWNER/ADMIN 可签发；
- 支持过期、撤销、最大使用次数；
- redeem 时重新校验群 active、容量、Block 和 invite 状态；
- 入群与 `use_count` 必须在同一 PostgreSQL transaction，避免次数与成员状态分叉。

### PC/Web 扫码登录

- nonce 使用 CSPRNG；
- 短 TTL；
- 服务端数据库只保存 nonce SHA-256，不保存原始登录 secret；
- scanner 用户与当前移动设备被服务端绑定；
- 手机端确认页面必须展示服务端 challenge 中保存的目标设备名称/平台/App 版本；
- approved 后创建目标新设备 Session 与 QR 一次消费在同一事务；
- 第二次 consume 不能签发第二套 Session；
- nonce 放 POST body，不放 URL path/query，降低 proxy/access log 泄露概率；
- reject/expired/consumed 均是不可逆终态。

当前 QR 服务端已自动验证，Flutter QR 自身旧 analyzer/tests 阻断也已修复并有定向通过证据；2026-08-12 本轮全 App analyzer 与 Flutter 全量测试已重新通过。当前 worktree 仍不能直接发布，剩余阻断主要是真实扫码/跨设备/真机 Push 与生产发布链验收，而不是 QR 服务端安全边界。

# 18. Web 安全

生产：

- HTTPS only。
- CORS 只允许显式可信 origin。
- WebSocket Origin 限制。
- CSP 后续上线管理/Web 正式生产时完善。
- 如果未来 Web 使用 Cookie session，必须有 Secure/HttpOnly/SameSite/CSRF 设计。

当前 Native Bearer Token 方案不能简单照搬成 Web localStorage 长期 token。

# 20. 日志

禁止记录：

- 密码。
- 邮箱验证码。
- Access/Refresh Token。
- presigned URL 完整 query。
- SMTP secret。
- S3 secret。
- LiveKit secret。
- Telegram Bot Token。
- 未来 E2EE private key。

允许记录的诊断字段：

- requestId。
- userId/deviceId（注意保留周期）。
- endpoint。
- status/error code。
- mediaId/uploadId。
- conversationId/messageId。
- 执行阶段和延迟。

客户端日志也不能因为“方便排错”打印 Token。

# 21. E2EE 当前真实状态

**当前 DD 没有正式 E2EE。**

消息正文可被服务端业务逻辑处理，例如：

- Mention parse。
- 服务端消息搜索。
- 内容 JSON。

因此当前只能宣称：

- 传输层 TLS（生产配置要求）。
- 服务端访问控制。
- 私有对象存储。

不能宣称：

- “服务器无法读取聊天内容”。
- “端到端加密聊天”。

未来设计见 `09-P0-E2EE候选库评估.md`。

# 22. 安全测试门槛

每个正式模块至少需要：

- 未登录 401。
- 非成员/非 owner 404 或 403（按隐私合同）。
- 横向 IDOR。
- 伪造 userId/mediaId。
- 并发/幂等。
- 限流。
- 无效 JSON/超大输入。
- Block 边界。
- 日志 secret 扫描。

媒体追加：

- purpose mismatch。
- sha/size mismatch。
- 过期 upload。
- 下载越权。
- orphan cleanup 引用安全。

Sticker 追加：

- arbitrary URL 拒绝。
- 非订阅用户重发 Telegram Sticker 拒绝。
- Token 未配置不影响 Custom Sticker。

Mention 追加：

- 伪 entity。
- overlap/越界。
- Email/`@@` 不误识别。
- Block user 不建议。

# 23. 漏洞处理原则

P0：

- 未授权读私聊/媒体。
- Auth bypass。
- Secret 泄漏。
- 任意文件/SSRF 到内网敏感地址。
- 任意加入通话。
- 消息/联系人跨用户篡改。

发现 P0 后：停止新增功能，先修复、加回归、轮换可能泄漏的 secret。
