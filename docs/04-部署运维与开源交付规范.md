# 部署、运维与开源交付规范

## 1. 交付目标

任何具备以下条件的用户，应能按文档搭建实例：

- 一台拥有公网 IPv4 或可正确映射公网端口的 Linux 服务器。
- 一个或多个域名。
- Docker Engine 与 Docker Compose Plugin。
- 可用 SMTP 发信能力。
- 能开放 HTTPS、WebSocket 和 WebRTC 所需端口。

“只要有公网服务器即可搭建”不等于零配置。邮件、TLS、推送和音视频网络都存在外部依赖，安装器必须检测并明确提示。

## 2. 支持的部署模式

## 2.1 单机 Docker Compose（首要支持）

适用：个人、小团队、小型社区。

组件：

- Caddy/Nginx。
- Core API。
- Worker。
- PostgreSQL。
- Redis。
- MinIO。
- LiveKit。
- 可选 coturn。
- 可选 Prometheus/Grafana/Loki。

目标：

```bash
git clone <repository>
cd <repository>
./scripts/install.sh
sudo docker compose up -d
./scripts/health-check.sh
```

Windows 仅作为开发环境；正式服务端优先支持 Linux。

## 2.2 外部托管依赖

部署者可替换：

- PostgreSQL。
- Redis。
- S3 对象存储。
- SMTP。
- LiveKit。

必须通过配置切换，不允许修改源码才能使用外部服务。

## 2.3 Kubernetes（后续）

只有在：

- 多节点 API。
- 独立媒体节点。
- 高可用数据库。
- 多地域部署。

确有需求时才提供 Helm Chart。首版不能把 Kubernetes 作为安装前提。

## 3. 域名规划

推荐：

- `chat.example.com`：Web 客户端。
- `api.example.com`：REST/WSS。
- `admin.example.com`：管理后台。
- `media.example.com`：对象存储/CDN。
- `rtc.example.com`：LiveKit。
- `turn.example.com`：TURN/TLS。

小型部署可以合并部分域名，但安装器必须处理证书和路由，不允许让用户猜。

## 4. 网络与端口

基础端口示例：

| 用途 | 协议 | 端口 | 说明 |
|---|---|---:|---|
| HTTP 重定向/ACME | TCP | 80 | 可选但常用 |
| HTTPS/WSS | TCP | 443 | 必需 |
| LiveKit Signal | TCP | 7880 | 通常经反代 |
| LiveKit RTC/TCP | TCP | 7881 | 按配置 |
| LiveKit RTC/UDP | UDP | 50000-60000 | 按配置开放 |
| TURN | UDP/TCP | 3478 | 按配置 |
| TURN/TLS | TCP | 5349 或 443 | 按配置 |
| TURN Relay | UDP | 配置范围 | 不能遗漏 |

端口范围必须以最终 LiveKit/coturn 配置为准。安装脚本应：

- 检查端口占用。
- 检查公网 IP。
- 检查 UDP 是否可能被云防火墙阻断。
- 输出云安全组和系统防火墙的明确清单。

## 5. 服务器规格

以下仅为保守起点，实际取决于在线人数、媒体使用和带宽：

### 纯聊天小实例

- 2 vCPU。
- 4 GB RAM。
- 50 GB SSD。
- 独立备份空间。

### 含音视频的小实例

- 4 vCPU。
- 8 GB RAM。
- 100 GB SSD。
- 足够的公网出站带宽和流量额度。

不确定点：音视频并发容量高度依赖分辨率、编码、网络和 TURN 中继比例，不能仅凭 CPU 核数承诺。发布前必须提供实际压测结果。

LiveKit 官方提醒生产扩展主要受 CPU 与带宽约束，并建议正确配置公网 IP、UDP、TURN 和 host networking：

- https://docs.livekit.io/transport/self-hosting/deployment/

## 6. 配置规范

### 6.1 配置来源

- 非敏感配置：版本化 YAML/TOML。
- 敏感配置：环境变量、Docker Secrets 或挂载 Secret 文件。
- `.env.example` 提供注释和安全默认值。

### 6.2 必填配置

- 实例名称。
- 公网 URL。
- 数据库连接。
- Redis 连接。
- 对象存储。
- SMTP。
- Token/Session Secret。
- 初始管理员邮箱。
- LiveKit API Key/Secret。
- TURN 域名和证书配置。

### 6.3 启动校验

服务启动前必须检查：

- Secret 长度和默认值。
- 数据库可连接且版本受支持。
- Redis 可连接。
- Bucket 存在且非公开。
- SMTP 可选测试。
- 公网 URL 使用 HTTPS。
- CORS 来源非通配符。
- 数据库迁移状态。

配置错误应直接拒绝启动，不能带着危险默认值运行。

## 7. 安装器

`scripts/install.sh` 应完成：

1. 检查 Linux、CPU 架构、Docker、Compose、磁盘和端口。
2. 交互式询问域名、管理员邮箱、SMTP、存储和注册模式。
3. 生成高熵 Secret。
4. 写入权限受限的 `.env`。
5. 拉取固定版本镜像。
6. 启动基础依赖。
7. 执行数据库迁移。
8. 创建初始管理员。
9. 启动全部服务。
10. 执行健康检查。
11. 输出下一步和防火墙清单。

安装器不得：

- 自动关闭系统防火墙。
- 把 Secret 打印到公共日志。
- 使用 `latest` 镜像标签。
- 未确认就覆盖现有 `.env` 或数据目录。

## 8. Docker 规范

- 镜像使用多阶段构建。
- 运行时使用非 root 用户。
- 基础镜像固定主版本并定期更新。
- 支持 amd64、arm64。
- 每个服务提供 Healthcheck。
- 文件系统尽量只读。
- 数据目录显式挂载。
- 设置 CPU、内存、PIDs、日志大小限制。
- 禁止把 `.env`、私钥、证书打进镜像。
- 生成 SBOM 并执行镜像漏洞扫描。

## 9. 数据持久化

需要持久化：

- PostgreSQL 数据。
- Redis 如仅缓存可不纳入关键备份；若承担队列则需明确恢复语义。
- MinIO/S3 对象。
- 配置、证书和 Secret。
- 审计日志。

不得依赖容器可写层保存永久数据。

## 10. 备份与恢复

### 10.1 备份

提供：

```bash
./scripts/backup.sh
```

功能：

- PostgreSQL 一致性备份。
- 对象存储清单或增量备份。
- 配置和版本信息。
- 加密归档。
- 校验哈希。
- 可选上传远端存储。

### 10.2 恢复

提供：

```bash
./scripts/restore.sh <backup-file>
```

流程：

1. 检查备份版本和哈希。
2. 停止写入。
3. 恢复数据库。
4. 恢复对象存储。
5. 执行必要迁移。
6. 启动服务。
7. 验证关键数据和健康检查。

### 10.3 恢复演练

每个发布版本至少验证：

- 从上一稳定版本备份恢复。
- 从当前版本备份恢复。
- 对象缺失和数据库缺失时能明确报错。

## 11. 升级与回滚

提供：

```bash
./scripts/update.sh
```

升级前：

- 获取目标版本 Release Manifest。
- 检查兼容性、磁盘、备份和迁移。
- 拉取固定版本镜像。
- 创建升级前备份。

升级中：

- 进入维护或只读模式。
- 执行向前兼容迁移。
- 滚动或有序重启。
- 健康检查。

升级后：

- 验证版本、数据库、WebSocket、SMTP、对象存储、LiveKit。
- 记录升级审计。

回滚：

- 应用镜像可以回滚。
- 数据库迁移不一定安全回滚，因此每次 Release 必须标注：可逆、不可逆、需要恢复备份。
- 禁止对不可逆迁移做虚假的“一键回滚”承诺。

## 12. 可观测性

### 12.1 日志

- JSON 结构化日志。
- requestId、userId 脱敏标识、服务名、版本、错误码。
- 日志轮转和容量限制。
- 默认不记录消息正文和敏感凭据。

### 12.2 指标

- HTTP 请求量、延迟、错误率。
- WebSocket 在线连接和断开原因。
- 消息发送、同步延迟和 Outbox 积压。
- Worker 队列和失败任务。
- PostgreSQL 连接、慢查询、锁等待。
- Redis 延迟和内存。
- 对象存储容量和错误。
- LiveKit 房间、参与者、丢包和带宽。

### 12.3 健康检查

- `/health/live`：进程是否存活。
- `/health/ready`：依赖是否可用、是否可接流量。
- `/health/version`：版本和构建信息，不泄露 Secret。

### 12.4 告警

- API 错误率。
- 数据库不可用。
- 磁盘不足。
- 证书即将过期。
- SMTP 连续失败。
- Outbox/Worker 积压。
- 对象存储容量阈值。
- LiveKit/TURN 不可达。

## 13. 推送现实限制

### Android

- FCM 依赖 Google。
- 可选 UnifiedPush 作为开放方案。
- 无推送服务时，后台可靠通知无法保证。

### iOS

- 可靠后台通知依赖 APNs。
- 每个部署者自行使用 Apple Developer 凭据并不现实，因此需要设计：
  1. 官方客户端 + 官方中继推送服务；或
  2. 部署者自行构建并签名客户端；或
  3. 只支持官方实例推送。

这是自托管 iOS 最大产品难点之一，必须在开工前确定商业和隐私边界，不能在发布前才发现。

### Web

- 浏览器 Push 依赖浏览器厂商推送基础设施。
- 前台可直接使用 WebSocket。

## 14. 开源仓库交付

必须包含：

- `README.md`。
- `LICENSE`。
- `CONTRIBUTING.md`。
- `CODE_OF_CONDUCT.md`。
- `SECURITY.md`。
- `CHANGELOG.md`。
- `.env.example`。
- Docker Compose。
- 安装、更新、备份、恢复脚本。
- 架构文档、API 文档、数据迁移文档。
- 示例截图使用虚构账号和数据。

## 15. 许可证建议

候选：

### AGPL-3.0

优点：

- 网络提供服务的修改版也需开放源代码。
- 防止他人拿去闭源改造后直接提供 SaaS。

风险：

- 部分企业和依赖生态不愿采用。
- 客户端、服务端、SDK 和第三方库的许可证兼容性必须审查。

### Apache-2.0

优点：

- 宽松、企业接受度高。
- 更利于生态和二次开发。

风险：

- 他人可闭源商用修改。

暂定建议：

- 服务端 AGPL-3.0。
- 协议、SDK 和部分客户端考虑 Apache-2.0。
- 正式确定前进行依赖许可证扫描和法律审查。

## 16. 发布渠道

- GitHub/GitLab Release。
- GHCR 或其他 OCI Registry。
- Android APK、F-Droid 候选、Google Play 候选。
- Windows 安装包。
- macOS 签名包。
- iOS TestFlight/App Store 候选。
- Web PWA。

每个二进制必须：

- 可追溯到 Git Commit。
- 有校验和。
- 有 SBOM。
- 有签名或可信发布证明。

## 17. Definition of Done：可自建

只有满足以下条件，才能宣称“任何人有公网服务器即可搭建”：

- 全新受支持 Linux 主机完成安装测试。
- 安装文档不依赖作者私有服务。
- SMTP、存储、域名、证书均有明确配置。
- 文本、媒体、WebSocket、语音和视频通过外网实测。
- 备份和恢复实测成功。
- 更新和失败回滚路径实测。
- amd64 和 arm64 镜像可用。
- 错误提示能指导修复，而不是只打印栈。
