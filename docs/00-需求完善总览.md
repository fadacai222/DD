## 1. 产品定位

DD 是一个可自托管、多端即时通讯产品。

核心产品原则：

- **信息架构与交互习惯参考微信的克制、直接、低学习成本。**
- **开放性、消息能力、性能、动画流畅度、媒体体验参考 Telegram。**
- 不复制微信、Telegram 的商标、名称、图标、声音、贴图或受版权保护品牌资产。
- 目标是商业化可用，不接受“工程 Demo 能跑”作为最终完成标准。
- 自托管是第一等能力，任何关键服务应有清晰部署、备份、升级和故障恢复路线。

## 4. 好友与关系链

当前关系状态至少包括：

```text
SELF
NONE
PENDING_OUTGOING
PENDING_INCOMING
CONTACT
```

Block 对公开查询采用“不存在/不可见”隐私语义，不能让第三方通过资料 API 探测“谁拉黑了谁”。

已实现：

- DDID 精确搜索。
- 好友申请、拒绝、取消、过期。
- 反向同时申请自动收敛。
- 接受申请原子建立双向 contacts + DIRECT conversation。
- 接受后写入“我刚刚同意了你的好友请求”系统消息并通过 Outbox 分发。
- 联系人备注、标签、星标。
- 删除好友不删除历史会话。
- 拉黑会删除联系人关系、取消申请并阻止新消息。
- 关系变化进入 `RELATIONSHIP` Outbox，用于实时刷新。

当前重点回归：正常联系人资料曾被大面积误显示“用户不可用”；代码已加入 Stable-ID API 与兼容 fallback，但必须真人复测。

## 6. 媒体、语音、视频与 Sticker

### 6.1 正式媒体模型

- PostgreSQL 保存媒体元数据与所有权。
- 对象内容走 S3/MinIO 兼容私有 Bucket。
- 客户端先申请 reservation，再直接 PUT 对象存储，最后 complete。
- 下载必须经过服务端授权并签发短期 URL。
- 取消上传必须真正关闭 HTTP transport，而不只是隐藏 UI。
- Worker 清理未完成上传与无业务引用 READY orphan。

### 6.2 本地缓存

- 图片/媒体使用本地缓存避免重复请求。
- 视频首播允许签名 URL streaming，同时后台落完整文件。
- 完整缓存使用 `.part`，成功后原子化可用。
- 401/403/410 可刷新一次下载 Grant。
- Web 不无限占用本地磁盘。

### 6.3 Sticker

自定义 Sticker：

- READY `STICKER` media 才可入库。
- PNG/WebP/GIF。
- 用户库、排序、批量删除。

Telegram Pack：

```text
Telegram setName
→ 服务端 Bot API 拉取
→ 下载 provider 文件
→ 写入 DD 私有对象存储
→ 产生稳定 DD mediaId
→ 用户订阅 pack
```

安全要求：

- 客户端只发送 `setName`，不能要求服务端抓任意 URL。
- Bot Token 只在服务端 secret。
- 用户仅收到过某 Sticker，不代表拥有再次发送权限。
- Telegram 官方 Sticker 格式按源类型做白名单校验：静态 WebP/PNG、动态 TGS（gzip Lottie）、视频 WebM；格式/内容损坏才计入导入失败，不再把合法 TGS/WebM 当 unsupported。

## 8. UI / UX 总原则

### 微信参考

参考：

- 四主入口信息层级。
- 联系人、聊天、我的的低学习成本结构。

### Telegram 参考

参考：

- 低延迟。

- Sticker/GIF/媒体开放性。
- 消息编辑/转发/收藏/置顶/搜索。

### 明确不参考

- 不采用 WhatsApp 式视觉作为目标。
- 不复制第三方品牌资产或通知音。
- 不为了像微信而复刻其产品限制，例如 2 分钟撤回硬限制。

## 10. 明确不允许的“伪完成”

以下情况一律不能标为完成：

- API handler 有代码，但 OpenAPI、客户端合同完全不同步。
- Widget Test 通过，但真人端明确功能失败。
- Catch 掉异常后 UI 不报错，就称“稳定”。
- 视频只 mock metadata，没有真实容器/真实客户端验证。
- Sticker 只在一个账号能显示，没有权限隔离测试。
- 通话只在 localhost/LAN 打通，就称“生产可用”。
- UI 能显示，但用户找不到入口。
- Android 通知只能下拉看到，没有按产品要求 Heads-up，却称“通知完成”。
