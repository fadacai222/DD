# 技术架构与模块设计

## 1. 架构目标

- 首版能由一台普通公网服务器部署。
- 小规模使用不需要 Kubernetes、消息队列集群或微服务治理。
- 代码模块边界清晰，未来可按压力拆分服务。
- Web、桌面和移动端尽量共用业务模型、协议和 UI 组件。
- 实时消息可靠，不把 WebSocket 当作唯一事实来源。
- 音视频不自行造轮子。
- 安全、审计、可观测性从第一阶段进入架构。

## 3. 技术选型

## 3.1 客户端：Flutter

选择原因：

- 官方覆盖 Android、iOS、Web、Windows、macOS 和 Linux。
- 同一套 Dart 领域模型、网络层、状态机和大部分 UI 可复用。
- 适合高度定制的聊天界面和跨端一致体验。
- LiveKit 提供 Flutter SDK 和 UI 组件生态。

代价：

- Web 首屏体积通常大于纯 React。
- 浏览器能力、后台通知和文件系统受 Web 沙箱限制。
- 个别桌面原生能力需要插件或平台通道。
- 不能迷信“100% 一套代码”；平台权限、通知、音频路由必须分别适配。

官方依据：

- https://docs.flutter.dev/reference/supported-platforms
- https://docs.flutter.dev/platform-integration/web

## 3.2 管理后台：React + TypeScript

管理后台与聊天客户端诉求不同：

- 表格、筛选、配置和监控面板更适合 Web 技术栈。
- 不需要打包到移动端。
- 可单独权限隔离和部署。

## 3.3 服务端：Go 模块化单体

选择原因：

- WebSocket 长连接、并发和网络服务资源占用可控。
- 单二进制和容器部署简单。
- 与 LiveKit、Pion 和云原生生态兼容。
- 比首版直接拆微服务更容易保证事务一致性和开发效率。

模块化单体不是“大泥球”。要求：

- 每个模块拥有自己的领域模型、服务接口和仓储接口。
- 禁止跨模块直接访问对方的数据表。
- 跨模块操作通过应用服务或领域事件。
- 模块公开接口必须有契约测试。

## 3.4 数据组件

### PostgreSQL

用于：

- 用户、设备、好友关系。
- 会话、成员、消息索引。
- 朋友圈、评论、点赞。
- 二维码令牌、举报、审计。
- 配置和任务元数据。

PostgreSQL 是唯一业务事实数据源。Redis 丢失后不能导致永久业务数据丢失。

### Redis

用于：

- 分布式限流。
- 在线状态和 WebSocket 节点映射。
- 短期验证码和扫码状态。
- 缓存和任务协调。
- LiveKit 多节点部署所需状态。

Redis 数据必须被视为可重建。

### MinIO / S3

用于：

- 头像、图片、语音、视频、文件。
- 客户端导出包。
- 备份文件。

对象使用随机不可猜测 Key，不使用原始文件名作为存储路径。

## 3.5 音视频：LiveKit

选择原因：

- 开源、自托管、基于 WebRTC。
- 支持 Flutter、Web、Android、iOS 等 SDK。
- 提供 SFU、弱网适配、Simulcast、TURN、端到端加密能力。
- 可从单机扩展到多节点。

官方依据：

- https://docs.livekit.io/transport/self-hosting/
- https://docs.livekit.io/transport/self-hosting/deployment/
- https://github.com/livekit/livekit

部署注意：

- 必须有可信 TLS 证书。
- 必须正确暴露 UDP/TCP 端口。
- Docker 生产部署优先 host network。
- TURN 需要单独域名和证书时，安装器必须校验。
- 媒体带宽成本可能远高于文本消息成本。

## 3.6 TURN：LiveKit 内置或 coturn

默认优先使用 LiveKit 推荐配置；复杂部署可使用 coturn。

- https://github.com/coturn/coturn

TURN 不能只开 3478 一个 TCP 端口就宣称可用；必须验证 UDP、TLS、外网映射和中继端口范围。

## 4.1 Auth 模块

职责：

- 注册、邮箱验证、登录、刷新、退出。
- 密码重置、TOTP、Passkey。
- 会话和 Refresh Token 轮换。
- 风险事件和异常登录通知。

不负责：

- 用户资料展示。
- 好友关系。
- 管理员用户查询。

## 4.2 Users 与 Devices

Users：

- 公开资料、账号短号、隐私设置。

Devices：

- 设备身份、推送 token、设备公钥、最后活动。
- 远程退出、设备验证、密钥状态。

多设备端到端加密要求“设备”成为一等实体，不能只在用户表放一个公钥。

## 4.3 Contacts

- 好友申请状态机。
- 好友关系、备注、标签、黑名单。
- 搜索策略和反枚举控制。

## 4.4 Conversations 与 Messages

Conversations：

- 单聊/群聊会话。
- 成员、角色、最后读序号、置顶、免打扰。

Messages：

- 消息信封、序号、发送者设备、类型、状态。
- 明文模式下的正文或 E2EE 模式下的密文载荷。
- 撤回和系统事件。

关键约束：

- 每个会话分配单调递增 `sequence`。
- `clientMessageId + senderDeviceId` 唯一。
- 服务端接受重试但不重复落库。
- 消息发送与 Outbox 事件在同一数据库事务提交。

## 4.5 Sync

同步不能依赖“当时在线就推到了”。

推荐模型：

- 全局事件游标负责用户级变更。
- 会话序号负责消息级顺序。
- WebSocket 只通知“有新事件”。
- 客户端按游标通过 REST/同步接口拉取权威数据。

好处：

- 断线可恢复。
- 推送丢失不丢消息。
- 多设备最终一致。
- 服务重启不会破坏消息可靠性。

## 4.6 Media

流程：

1. 客户端申请上传。
2. 服务端检查配额并生成预签名 URL。
3. 客户端直传对象存储。
4. 客户端确认上传。
5. Worker 校验、扫描、生成派生文件。
6. 媒体进入可发送状态。

禁止客户端仅凭一个任意 URL 构造媒体消息。

## 4.7 Calls

- 业务服务维护呼叫状态和权限。
- LiveKit 负责媒体房间。
- 服务端为合法参与者签发短期 LiveKit Token。
- 客户端不能自行指定任意房间并获得权限。

## 4.8 Moments

- 帖子、媒体关联、受众规则、点赞、评论。
- 发布时保存受众策略快照或可验证规则。
- 查询时必须在数据库层执行可见性过滤，不能仅依赖客户端隐藏。

## 4.9 QR Code

二维码只承载：

- 版本号。
- 类型。
- 短期随机 token 或公开短码。
- 实例标识。

不得包含密码、邮箱、Refresh Token、内部数据库主键或可直接执行管理员动作的数据。

## 5. API 设计

### 5.1 协议

- REST：注册、资料、好友、会话、历史、朋友圈、配置。
- WebSocket：实时事件通知、呼叫信令、在线状态。
- WebRTC：音视频。
- 预签名 URL：媒体上传下载。

### 5.2 版本

- `/api/v1/...`
- WebSocket 握手声明协议版本。
- API 只做向后兼容增加；删除字段需要弃用周期。

### 5.3 错误格式

```json
{
  "error": {
    "code": "CONTACT_REQUEST_RATE_LIMITED",
    "message": "操作过于频繁",
    "requestId": "req_xxx",
    "details": {}
  }
}
```

生产环境不返回栈信息、SQL、内部路径和第三方密钥。

## 6. 消息可靠性设计

## 6.1 发送链路

```text
客户端生成 clientMessageId
  → POST/WS 发送命令
  → 鉴权与成员权限检查
  → 数据库事务写 Message + Outbox
  → 返回正式 messageId/sequence
  → Dispatcher 消费 Outbox
  → 在线设备 WebSocket 通知
  → 离线设备 Push 通知
  → 客户端通过 sync 确认权威状态
```

## 6.2 Outbox Pattern

目的：避免“消息写入成功但推送事件丢失”。

- 消息和 Outbox 事件同一事务。
- Dispatcher 至少一次投递。
- 消费者必须幂等。
- Outbox 可按时间归档和清理。

首版可用 PostgreSQL Outbox，不急于引入 Kafka/NATS。

## 6.3 顺序

- 只保证单会话内的服务端序号顺序。
- 不保证不同会话之间的绝对顺序。
- 客户端本地乐观消息最终以服务端序号校正。

## 7. 客户端架构

```text
clients/flutter_app/
├─ lib/
│  ├─ app/
│  ├─ core/
│  │  ├─ network/
│  │  ├─ storage/
│  │  ├─ crypto/
│  │  ├─ permissions/
│  │  └─ design_system/
│  ├─ features/
│  │  ├─ auth/
│  │  ├─ contacts/
│  │  ├─ chat/
│  │  ├─ calls/
│  │  ├─ moments/
│  │  ├─ qr/
│  │  └─ settings/
│  └─ platform/
├─ test/
└─ integration_test/
```

原则：

- 领域模型与 API DTO 分离。
- 本地数据库作为 UI 数据源，网络同步写入本地库。
- UI 不直接依赖 HTTP 响应临时对象。
- 发送队列支持离线、重试和幂等。
- 密钥只存系统安全存储，不存普通 SharedPreferences/localStorage。

推荐本地数据：

- SQLite/Drift：会话、消息索引、联系人和同步游标。
- 安全存储：Refresh Token、设备私钥。
- 文件缓存：缩略图、语音和媒体缓存。

## 9. 扩展路径

### 小型单机

- Core API 1 实例。
- Worker 1 实例。
- PostgreSQL、Redis、MinIO、LiveKit 同机。

### 中型部署

- API 多实例。
- Redis 共享在线状态。
- PostgreSQL 独立服务器。
- 对象存储独立。
- LiveKit 独立媒体节点。

### 大型部署

- 将 Media、Notification、Sync 等高压力模块拆服务。
- 引入 NATS/Kafka 前必须先证明 PostgreSQL Outbox 成为瓶颈。
- LiveKit 多节点和地域部署。
- 数据库读副本、分区和归档。

## 10. 明确反对的方案

- 首版直接使用几十个微服务。
- 自己实现 WebRTC SFU。
- 自己发明端到端加密算法。
- 使用 Redis 作为永久消息库。
- 只靠 WebSocket 推送，不做离线同步。
- 媒体文件全部穿过 Go 应用进程上传。
- 用客户端时间作为消息权威顺序。
- 把 JWT 永久存 localStorage。
- 为了“完全去中心化”在首版引入跨实例联邦。
