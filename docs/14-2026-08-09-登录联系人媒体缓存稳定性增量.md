# 1. 自动登录与历史账号

## 原问题

每次打开都要求重新输入账号，缺少成熟 IM 的历史登录体验。

## 当前实现

状态：`IMPLEMENTED`

客户端已经有：

```text
auth_boot_page.dart
auth_session_vault.dart
login_history_store.dart
login_history_backend*.dart
```

启动：

```text
读取 secure session
→ refresh
→ MainShell
```

历史账号卡片保留头像/昵称等非敏感信息。

## 稳定性规则

- Temporary network error：不清 Refresh Token。
- Explicit unauthorized/revoked：清当前失效 session。
- 不先闪 Login 再进入 MainShell。
- 多个 secure-storage 写操作要串行/防损坏。

# 2. 联系人实时刷新

## 原问题

加好友后要“大退重开”才看到；新申请/同意没有第一时间刷新。

## 当前实现

状态：`IMPLEMENTED`，真人继续回归。

服务端：

```text
000012_relationship_outbox
RELATIONSHIP outbox events
accept transaction
friend accepted SYSTEM message
```

客户端：

- `MessagingCoordinator.relationshipNotices`。
- `MainShellPage` 监听关系事件。
- 收到好友通过 SYSTEM message 也触发 contacts refresh。
- “新的朋友”使用真实 request list。

## 验收

A/B 双端必须做到：

```text
A 发申请
→ B 不重启看到
B 同意
→ A 不重启关系更新
→ 双方联系人出现
→ 聊天系统消息出现
```

# 3. 联系人资料稳定 ID

## 原问题

列表拿到 user 后，资料页再按错误/旧路径查找可能失败，甚至把正常用户显示成“不可用”。

## 当前实现

状态：`FIXED-PENDING-RETEST`

新增/使用：

```text
GET /api/v1/users/{userId}
```

资料跳转以 stable UUID 为主。

兼容旧开发服务端时，客户端只有在 handle/contact list 能证明 **同一 userId** 时才 fallback。

## 错误分类

必须区分：

```text
404 privacy/not found
401 session
5xx server error
network timeout
invalid JSON/client contract
```

只有 404 类才允许展示“用户当前不可用”的隐私文案。

# 5. Download Grant 缓存

短期 presigned URL 不等于长期缓存资源。

客户端可以缓存：

```text
mediaId → grant + expiresAt
```

但：

- 到期前才复用。
- 401/403/410 只刷新有限次数。
- 不把 presigned URL 写入长期日志。

真正长期复用的是本地媒体 bytes。

---

# 6. 图片/文件本地缓存

Native：

- 应持久到 app cache/support directory。
- key 以 stable mediaId + 必要版本信息。
- 同资源 in-flight 请求合并。
- 下载 `.part`。
- 完成校验后 atomic rename/commit。

Web：

- 不依赖无限磁盘路径。
- 浏览器缓存/内存策略与 Native 分开。

---

# 7. 视频缓存

## 首播

产品目标不是“必须完整下载才开始”。

优先：

```text
signed URL streaming
+ background complete cache
```

## 二次打开

```text
complete local file
→ play local immediately
```

## 完整性

只有：

- 下载完成。
- size 符合 expected。
- 必要 metadata 可读。

才把 `.part` 变正式 cache。

# 9. 媒体焦点加载

列表性能原则：

- 当前可见/接近 viewport 的媒体优先。
- 不可见 GIF/视频不要持续解码。
- 图片使用展示尺寸匹配的 decode/cacheWidth。
- Sticker 大 grid 不能一次解码全部动画。

这比“进页面就把所有聊天媒体全部 preload”更可控。

# 11. 上传取消

稳定性增量要求：

> Cancel 不能只是把进度条隐藏。

当前上传 transport 应可通过 client/stream cancellation 真的终止。

测试：

1. 开始大文件上传。
2. 观察网络流量。
3. 点取消。
4. 请求尽快停止。
5. 服务端 reservation 最终由 cleanup 处理。

---

# 12. Retry 策略

可重试：

```text
timeout
408
429
5xx
transport reset
```

谨慎/不自动重试：

```text
400 contract error
401 auth invalid（先 refresh）
403 authorization
404 resource missing
409 business conflict
413 too large
422 validation
```

PUT 对象失败后优先重新 reserve，避免出现：

```text
新内容
→ 旧 reservation
→ Uploaded object does not match reserved media
```

---

# 13. 媒体缓存清理

Native cache 必须有上限。

策略至少：

- age。
- LRU。
- total byte budget。
- startup 不同步扫描几万个文件阻塞首屏。

正在播放/正在保存/正在上传的文件不能被 cleanup 删除。

---

# 14. Realtime + Cache 关系

消息 realtime event 到达后：

- 立即显示消息 metadata/bubble。
- 不强制立刻下载所有 media bytes。
- 对当前可见媒体按优先级加载。

这样可以避免“群里来 20 个视频就瞬间把手机带宽打满”。P8 Moments 也沿用同一原则：Feed 只按可见区域获取短时 grant/媒体内容，不能因为打开朋友圈就预拉全量视频。
